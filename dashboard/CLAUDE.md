# dashboard

The forge dashboard workspace. Read-only view of `~/.forge/forge.db` plus an HTTP server that serves agent results as markdown cards. Shells out to `forge` for its closed set of mutations (the four `forge queue` verbs, `forge projects classify`, the three task actions — `forge gate`, `forge retry` and `forge recover --re-drive` — and the three attention-row actions, `forge attention dismiss|snooze|undismiss`, and the two RACI actions, `forge raci propose|apply`, and the two model-policy actions, `forge model policy propose|apply`, and the two attribution actions, `forge config set|unset ai-attribution`, and the one ticket-body edit, `forge backlog edit <id> --body -`) — never writes the DB directly. Next, cancel and dispatcher arming stay CLI-only.

## Layout

- `src/server.ts` — HTTP server (~1,000 LoC). Routes the read API, the closed set of mutating POSTs, and serves the shell.
- `src/queue-mutation.ts`, `src/action-mutation.ts` — the two closed mutation registries (queue planning; task, attention-row and RACI actions, FG-822/FG-823/FG-834); `src/raci-mutation.ts` — the RACI rows' body, proposal window, scratch candidate and `GET /api/raci` read model; `src/model-policy-mutation.ts` — the same for the model-policy rows and `GET /api/model-policy` (FG-835); `src/ai-attribution-mutation.ts` — the attribution rows and the Projects cards' attribution (FG-845); `src/backlog-edit-mutation.ts` — the ticket-body edit row and `GET /api/backlog/:id/readiness` (FG-847); `src/mutation-guards.ts` — the guards and the `forge` child all share.
- `src/roles.ts` — the Roles surface (FG-817): `GET /api/roles` and `GET /api/roles/:role`, assembled from the installed seeds, the seed generation, the model policy and `queries.ts`'s role reads; the pure seed derivations live in core's `src/v2/role-surface.ts`.
- `src/queries.ts` — `better-sqlite3` reads against `~/.forge/forge.db`. Row types imported from `@forge/types` (forge's `src/types/index.ts`); schema drift surfaces as a TypeScript error here.
- `src/shell.ts` — the HTML shell + CSS (template literals).
- `client/main.js`, `client/renderers.js` — browser JS, served as static files (no build, no bundling).
- `client/backlog.js` — read-only backlog view (`#backlog[/<ticketId>]`); mirrors `/api/backlog`. No writes. Its type/status filter state, hash and "N of M tickets" count are pure helpers in `client/backlog-state.js` (FG-832). It renders tickets only; session-handoff notes are the Notes view's (FG-830).
- `client/ops-window-state.js` — the Ops runtime window and summary since: hash state, the per-metric load reducers and the abortable, budgeted reader (FG-836). No DOM, fetch and timers injectable; unit-tested in `src/fg836-ops-loading.test.ts`.
- `client/notes-render.js`, `client/notes-view.js` — the Notes view (FG-830): `#notes` lists one row per checkout with a note, and `#notes/<checkout>` is that checkout's note page. Both read `/api/backlog`'s `notesByCheckout`; the pure row rules (session date, preview, order, primary) are in `notes-render.js`.
- `client/view-routing.js` — the closed `ROUTES` table and the only hash parser/writer (FG-820).
- `client/governance.js` — the read-only Routing workbench (SOURCE / DERIVED / EFFECTIVE / RECORDED); `client/raci-editor-view.js`, `client/raci-editor-state.js` — its Edit RACI mode (FG-834; see RACI authoring below).
- `client/models-editor-view.js`, `client/models-editor-state.js` — Setup › Models, the model-policy page and editor (FG-835; see Model-policy authoring below). They reuse the FG-834 machine and components (`raci-editor-state.js`'s gate adapter, `raci-editor-view.js`'s `CodeEditor`, `ErrorNote`, `Pill`, `ApplyCard`).
- `client/nav-render.js`, `client/nav-view.js` — the left-column navigation, the narrow-screen bottom bar and drawer (FG-820).
- The cockpit object pages (FG-821), each a pure `*-render.js` (unit-tested, no DOM) beside its `*-view.js`:
  - `client/runs-index-render.js`, `client/runs-index-view.js` — the run index (`#runs[?scope&status=]`) and the Runs badge.
  - `client/run-page-view.js` — the run page (`#run/<runId>[/map|/evidence]`); `client/run-map.js` draws its map tab.
  - `client/task-page-view.js` — the task page (`#task/<taskId>`) and its Explain page (`#task/<taskId>/explain`, body from `client/run-explain-panel.js`'s `ExplainContent`).
  - `client/ticket-page-view.js` — the ticket page (`#backlog/<ticketId>`); `ReviewPage` in `client/reviews.js` is a review by id (`#reviews/<reviewId>`).
  - `client/roles-index-render.js`, `client/roles-index-view.js` — the Roles list (`#roles`, FG-817; sortable headers and the pure `sortRoles` comparator, FG-828).
  - `client/role-page-render.js`, `client/role-page-view.js` — a role page (`#roles/<role>[/<tab>]`, FG-817; the grouped sub-nav, header meta line and Overview cards, FG-837).
  - `client/role-glyph.js`, `client/role-glyph-view.js` — the role glyph tile (FG-829): the family colour table, the glyph map, `roleFamily`/`roleTile` (pure, an SVG string) and the `RoleTile` Preact element drawn from the same parts.
  - `client/breadcrumbs-render.js` — trails and Escape-to-parent; `client/screen-header-render.js` — the screen contract (object pages' live lines, list views' `LIST_HEADERS`); `client/info-tip.js` — the list-view info tip (FG-838); `client/object-page-view.js` — the shared head, tabs and Escape handling.
- `client/checkout-label.js` — the one checkout label rule (FG-831): `checkoutLabel`, `checkoutLabelForDir`, `checkoutOptions`; and the header chooser's model (FG-843): `checkoutChooser`, `checkoutKindForDir`, `defaultCheckout`. `client/checkout-chooser-view.js` renders the chooser.
- `client/status-tokens.js` — the one status vocabulary (FG-824); `client/format.js` — the one formatter module (FG-824; it absorbed `duration.js`).
- `client/recovery-card-render.js`, `client/recovery-card-view.js` — the task page's recovery card (FG-824).
- `design/` — Pencil design corpus (`dashboard.pen` + PNG exports).

## Run

From the forge repo root:

```bash
./bin/forge-dev dashboard start    # boots tsx src/server.ts in this dir on port 8024
npm --workspace=dashboard typecheck
```

`./bin/forge-dev dashboard start` is the source-checkout entry. But the dashboard is now bundled into the promoted release as a mandatory asset (FG-580), so `forge dashboard` also runs from a promoted release — resolution is release-owned (it flows from `assetRoot()`, the executing release or the dev checkout, never the invocation cwd), and the FG-569 release-mode refusal is retired. The bundled UI boots offline: its client libs are vendored in-closure and served under a `script-src 'self'` CSP, so no CDN-executed JS is fetched (provider/data APIs may still need network). A torn/incomplete release — a missing dashboard file, vendored client lib, or dashboard-relevant dep — still fails named and nonzero (`assertDashboardClosure`) rather than falling back to a source checkout.

## Navigation (FG-820)

The plan is `docs/research/dashboard-information-architecture.md`. The 13-button tab strip is gone; there is no flag or twin keeping it alive.

- **Left column.** A scope control at the top — the project select and nothing else ("All projects" or a project; FG-843 removed the checkout chips, the "all checkouts" pill, the "show N missing" line and "clear ×"), then five groups under plain, non-collapsible headings, then the last-poll clock. Now: Home, Activity. Plan: Backlog, Notes, Queue, Campaigns. Evidence: Runs, Reviews, Shipping. Setup: Roles, Routing, Config, Projects. Health: Usage, Ops. Runs is the run index (FG-821); Roles is the Roles list (FG-817).
- **Keyboard (FG-692).** Every item is an `<a href="#…">`; group headings are not controls; `aria-current="page"` marks the current item; a "Skip to content" link comes first and the tab order is column → content. An object page highlights its parent (a run page highlights Runs).
- **Below 720px** (the nav breakpoint; 520/600/640 stay content breakpoints) the column is replaced by a fixed, safe-area-padded bottom bar — Home, Runs, Queue, Backlog, More. More opens a drawer holding the full column: a modal dialog that traps focus, closes on Escape, and returns focus to More.
- **`ROUTES` (`client/view-routing.js`).** A closed table: each view names its group (`now | plan | evidence | setup | health`), path pattern, scope requirement (`none | optional | project | checkout`) and legacy aliases. `parseHash` returns view, object id, tab and scope; unknown parameter keys are dropped; an unknown view lands on Home with a one-line "No view named …" notice. **The group is derived from the view, never read from the hash** — a `group=` parameter or a group-shaped leading segment (`#plan/queue`) is dropped and the URL rewritten with `history.replaceState`.
- **Aliases.** `#governance` → `#routing`, `#control-plane` → `#config`, `#run-map/<id>` → `#run/<id>` (the run page's default `map` tab; FG-821 — keep this alias permanently, saved and emitted `#run-map/<id>` links must resolve forever). A bare object hash (`#run-map`, `#run`, `#task`) lands on the run index with an "open a run from the run index" prompt. Every alias is rewritten to its canonical hash in place.
- **Object tabs.** Object routes name their tabs in `ROUTES` (`run`: `map`, `evidence`; `task`: `detail`, `explain`; `roles`: `overview`, `instructions`, `harness`, `skills`, `capabilities`, `tools`, `secrets`, `tasks`, `receipts`, `usage`). The first is the default and is omitted from the canonical hash; an unknown tab falls back to it. A route may map a retired tab name onto its successor (`tabAliases`: roles' `configuration` → `harness`), so an old link lands on the renamed tab and is canonicalized to it. `notes` takes an optional checkout segment, `#notes/<URI-encoded checkout directory>`, and has no tabs. A route may also own extra hash parameters (`params`: the run index's `status=`, the Roles list's `family=`/`sort=`/`dir=`, the Backlog's `type=`/`status=`), optionally closed to a vocabulary (`paramValues`: an unknown value is dropped from the canonical hash); a route's params belong to its list, so an object hash (`#roles/<role>`) carries none; every other key is still dropped.
- **Scope lives in the hash.** List views carry `?project=<projectKey>`; only Routing, Config and Notes (`checkout: true` in `ROUTES`, plus a role page's FG-835 resolution provenance) also carry `&checkout=<URI-encoded projectDir>` — any other view drops it on canonicalization (FG-843). Together they are mapped one-to-one onto the server's `?projectKey=`/`?projectDir=`. A scope change rewrites the hash with `replaceState`; moving between list views keeps it; scope-less views (`#projects`, the `#roles` list) and object hashes (`#run-map/<id>`) carry none and leave the scope in hand untouched. A role page (`#roles/<role>[/<tab>]`, route scope `object`, FG-835) is the exception: it carries scope, so its Harness rows resolve at the checkout its link named. Never `localStorage`/`sessionStorage`. The Remote Board must not adopt this scheme — the checkout parameter puts a host path in the URL.
- **No client-computed counts.** There are two nav badges. Home's is the attention envelope's server-computed `counts` (`src/v2/attention-inbox.ts`, the same derivation `forge attention list` prints): `counts.open`, danger-toned when `counts.high > 0`, a partial marker when `degraded` is non-empty, "?" when the read failed or carries no valid `counts`, hidden only when `empty: true`, capped at "99+". Never `items.length`, a per-view tally, a filtered-list count, read/unread state, or anything stored. The inbox is read on every view so the badge is live everywhere. Runs' is `GET /api/runs`'s server-computed `activeCount` (the derivation `forge runs query --status active` prints; `runs-index-render.js`'s `runsBadge`): an informational live count, never danger-toned, "?" when the read failed or carries no integer `activeCount`, hidden at 0, capped at "99+". It is read at 30s on every view, and the run index hands up its own first-page response so on `#runs` the badge is the list's own answer. Never `runs.length` or a count of a filtered or paged list.

## Checkout scope (FG-843)

- **Selecting a project selects its primary checkout, silently.** The scope column is the project select only. No view but Routing, Config and Notes reads one checkout's files, so every other view sends `?projectKey=` alone and reads the whole project (every checkout).
- **Operator vs run checkouts — one rule, in `src/queries.ts` (`checkoutKind`).** An **operator** checkout is one of the registry's own rows: the project's primary, a directory registered as a project (`forge projects classify <dir> --purpose operator`, the `workspace_purposes` row the projects index reads). Nothing else promotes a checkout: a live interactive session is not registration, so `liveSessions` stays a displayed fact and a run clone an operator opens is still a run checkout — a second working copy becomes operator by `forge projects classify <dir> --purpose operator`. Every other checkout exists only because a run or task executed there (agent clones, `~/.forge/worktrees/*`, per-ticket clones): a **run** checkout. Run checkouts stay on the record — their runs keep their project, scope and FG-831 label — but are never offered by the chooser. `GET /api/projects` serves the kind per checkout and `checkoutCounts`; the client never re-derives it.
- **The three choosers.** Routing, Config and Notes put `checkout: <label> ▾` in their screen header (`client/checkout-chooser-view.js`, model `checkoutChooser` in `checkout-label.js`) when the project has two or more **live** operator checkouts: a button + listbox of those checkouts, primary first and marked, each with its home-relative path, and a footer counting the run checkouts "listed on their runs, not here". With one, the header shows the label as plain text. Keyboard: Enter/Space/ArrowDown open, arrows/Home/End move, Enter picks, Escape or Tab closes, focus returns to the button. On Routing and Config a pick rewrites `?checkout=` in place (`replaceState`) and the view re-reads; on Notes it opens that checkout's note page. No other view renders a chooser. A pick scopes only that view's own read (the governance panel, the config graph) — the shared project reads (Activity, in-flight, the attention inbox, the nav badges) stay on the project key and keep polling every checkout's work (FG-843 RF-2).
- **Run-checkout deep links are honoured.** `#routing|#config?checkout=<run clone>` and `#notes/<run clone>` open that directory (a link from a run page still works); the chooser marks it `run checkout` and offers the operator checkouts, even when there is only one.
- **An unknown `?checkout=` canonicalizes to the primary.** A hash naming a directory the loaded project does not know (`checkoutForDir` finds nothing) is not honoured as a run checkout — it is unknown, the FG-828 pattern for any unrecognized hash value — and the chooser and the checkout-scoped read both fall back to `defaultCheckout` (the primary), rewriting the hash in place.
- **A run recorded through a symlinked parent resolves by path-identity, not by spelling.** `checkoutForDir` matches a directory against each checkout's full `projectDirs` set (every spelling the registry observed under it, FG-693's canonical grouping) as well as its root, so a run whose `project_dir` was written through a symlinked ancestor still labels and scopes under the physical checkout it names — Runs rows included — never under an alias treated as its own checkout.
- **Notes** lists operator checkouts' notes first, then run checkouts' notes under a "Run checkouts" caption.
- **Runs** keeps the cross-checkout listing with FG-831's label per row; the Projects card keeps every checkout and the missing count with `forge projects prune --missing`; a card or checkout row opens Activity scoped to the project.

## Object pages (FG-821)

- **No modal overlays for task detail or Explain.** Every entry point — feed cards, inbox rows, in-flight and orchestrator rows, current-activity rows, run map nodes — is (or navigates to) a link: a task row opens `#task/<taskId>`, a run-map node opens `#task/<taskId>/explain`, an inbox run row opens `#run/<runId>`. The task page and its Explain page link to each other as tabs.
- **Object pages read by global id, unscoped.** The run, task, Explain and review pages ignore the scope in hand, so an inbox click and a pasted link read the same object. The ticket page is the exception: ticket ids are per project, so `GET /api/backlog/:id/runs` and the ticket's fields are read with the list scope.
- **Breadcrumbs on object pages only, built from the payload, never from history:** Project › [Ticket ›] Run › Task › Explain. Every crumb but the last is a link; Project resolves to `#runs?project=<key>` (matched from the payload's `projectDir` against `/api/projects`, or the backlog's `ticketsProjectKey`). The ticket crumb comes from a `links.ticketId`: `GET /api/task/:id`'s for the task page, `GET /api/run/:id/evidence`'s for the run page. List views show group and title instead.
- **Screen headers: title + live state only (FG-838).** A list view renders its title and, where one exists, a live count (Runs' "N runs are active") — nothing else. Its contract (what is happening, whether it needs you, what to do, the CLI verb) is the `LIST_HEADERS` entry shown in the info tip beside the title: a 20px "?" button in the faint token, a hover/focus tooltip, and a click/Enter/Space popover (a dialog that takes focus; Escape or a click outside closes it, focus returns to the "?") with the verb as code and a Copy button. One `InfoTip` in `main.js` serves every list view; add a view's copy to `LIST_HEADERS`, never per-view markup. "Source: …" captions go in a footer under the content, not between the title and the content.
- **Screen line.** An object page states what is happening, whether it needs you, and what to do in one line, naming the next CLI verb where one applies — live facts only: a sentence that reads the same for every object is filler and does not belong in it. Object-page copy is read from the payload — the task's status and failure kind, and `GET /api/attention-inbox?runId=`'s `reason`/`requestedAction` (for a failed task that is the retry policy's advice). A task at `awaiting_gate` names `forge gate <id>`; a failed one `forge show <id>`.
- **Escape on an object page navigates to its parent:** Explain → task → run → `#runs`; ticket → `#backlog`; a note → `#notes` (scope kept); review → `#reviews`; a role page (any tab) → `#roles`. A key typed into a field, or an open modal (the nav drawer), is left alone.
- **Run evidence** (the `evidence` tab) is one `GET /api/run/:id/evidence` read per run visit — the server's own union of the run's reviews, launches and host verifications by run id (`queries.ts`'s `runEvidence`), not a client-side fold over each task's `links`. Reviews link to `#reviews/<id>`, launches to `/api/launches/<id>` and its `/log`, host verifications to the run's first task's Explain page (which shows the evidence).

## Roles (FG-817)

- **Every installed seed is an object.** `#roles` lists each directory under `$FORGE_HOME/agents` that carries a `CLAUDE.md`: its first paragraph, default activity (`defaultActivityForRole`), the profile/model/effort model policy resolves for that activity (`resolveModel` under the current seed generation), its `/project` mount and its last task. `#roles/<role>/<tab>` is a role page, deep-linkable, with `overview` the default (omitted from the canonical hash) and an unknown tab falling back to it. Tabs use the FG-821 tablist; the trail is Roles › `<role>` › `<tab>`. The list's headers (Role, Default activity, Resolved profile, Mount, Last task) are buttons that sort the fetched payload client-side (FG-828): first click ascending, second descending, `aria-sort` and a glyph on the active column; missing values (no default activity, a legacy or unresolved profile, never ran) sort last in both directions, ties by role name ascending, and Last task sorts on the ISO timestamp. The sort rides the hash as `#roles?sort=role|activity|profile|mount|lastTask&dir=asc|desc` — only a header click writes it (the nav link stays `#roles`), and an unknown value falls back to role ascending.
- **FG-837: the list and page after Paperclip** (the approved `roles-mock` / `role-page-mock`). The list is the Setup kicker and title, a one-line lede ("What each role is and runs on. A seed changes only through `forge upgrade`."), then a toolbar: family filter tabs — All, Builders, Reds, Research, Testers, Reviewers, Planners, Authors, the FG-829 families, a family with no installed role hidden (a selected one stays) — with the count (`23 roles`) and the current sort (`sorted by name ▲`) on the right. Rows sit in one bordered panel: the 36px tile (`TILE_SIZES.list`), the name with a one-line subtitle (`roleSubtitle`: the description's first sentence, Markdown stripped, cut at a word with an ellipsis past 120 characters and `text-overflow: ellipsis` on screen — it never wraps), the model in mono over the profile (and effort), `family · activity`, the last task through `formatRelativeTime` (`never` when none), and the mount as a pill (read-write in `--accent`, read-only in `--err`). The whole row opens the role (FG-849: a click handler on the `<tr>`, not a stretched `::after` overlay); a missing `settings.json` is a small badge after the name. The FG-828 header buttons stay — in the mock's column order, Role, Model, Family · activity, Last task, Mount — drawn as a light caption row; the Source line is the footer. The family tabs are toggle buttons (`aria-pressed`) in a `role="group"` labelled Family; a click writes `#roles?family=<build|red|research|test|review|plan|author>` and keeps `sort`/`dir`, a header click keeps `family`; filtering and sorting reorder the one fetched payload, and an unknown family is dropped from the hash. A role page is a trail, then — at 900px and wider — a grouped left sub-nav, a plain `nav` ("Role views") of links with `aria-current="page"` on the open tab and a 15px line icon each: **Role** (Overview, Instructions, Skills), **Runtime** (Harness / Runtime, Secrets, Tools), **Governance** (Capabilities / Trust, Receipts), **Audit** (Tasks, Usage). Under 900px the same tabs render as the FG-817 tablist instead (`matchMedia`, never both). The head is the 48px tile (`TILE_SIZES.page`), the name as `h1`, one meta line `runtime · model · family · mount` and the `forge upgrade` / `forge model resolve <role>` hint over a rule. Overview is a latest-task strip (FG-824 token, task id, run title, relative time), then Identity, Harness / Runtime, Capabilities and Skills cards (label/value `role-kv` grids, each linking to its tab), a full-width Last 30 days card (success rate, median duration, tokens), and Recent tasks rows with See all → Tasks. The other tabs keep their FG-827 content in the same panel/card vocabulary. Secondary text is `--fg-dim`, never `--fg-faint` (under 4.5:1 on `--bg`); `browser-tests/fg837-roles-parity.test.ts` computes every new text element's contrast.
- **FG-849: row activation is a click handler, not a stretched overlay.** The FG-837 shape used `.roles-ident a::after { position: absolute; inset: 0; }` anchored on a `position: relative` `<tr>`; WebKit does not treat a positioned `<tr>` as that overlay's containing block, so it escaped to the nearest one outside the table and spanned the whole list — the last row in DOM order took every click in Safari (not reproducible in headless Chrome, which does honour the positioned `<tr>`). Both rules are gone from `src/shell.ts`. Each row now carries `data-row-href=${r.href}` and `onClick=${openRoleRow}` (`client/roles-index-view.js`); `openRoleRow` reads `roleRowClickHref` (`client/roles-index-render.js`), which returns the row's href only for a plain primary click — no modifier or middle button, not already `defaultPrevented`, no text selection, and no `event.target.closest(ROLE_ROW_CONTROLS)` match (`a, button, input, select, textarea, label, [role=button]`) — otherwise it defers to the browser. The row's link is still the row's only tab stop (FG-692); the `<tr>` handler adds none. `src/fg837-roles-parity.test.ts` pins the CSS shape (no `::after` overlay, nothing positioning the `<tr>`) and the `roleRowClickHref` decision table; `browser-tests/fg837-roles-parity.test.ts` clicks a non-link point of the first, middle and last row, confirms a modifier click, a middle click and the row's own link are all left to the browser, and adds a keyboard case: Tab from the family tabs reaches the first row's link, and Enter opens it (FG-692).
- **Ten tabs, each captioned with its source** (`source` on each tab's payload, printed as a "Source: …" footer under the tab's content, FG-838): overview, instructions, harness, skills, capabilities, tools, secrets, tasks, receipts, usage. Instructions is `composeSystemPrompt`'s own output for `forge invoke <role>` with no project anchored (so no project addendum appears; the segmenter marks one when present), shown as marked sections — protocol, role seed, addendum, workflow additions, each constraint, framing — that concatenate to the exact bytes, with the sha256 of those bytes. A role dispatch would refuse (a covered role with no current protocol) shows the refusal instead. Secrets is the literal "none: containers receive no project secrets"; tools lists `settings.json`'s `tools`, flagged declared-not-enforced, MCP none; usage names ceilings as a future ticket.
- **FG-827: the tabs and their sources.** Instructions (`client/instructions-panel-render.js` / `-view.js`) is a Files panel over `instructions.files[]` — protocol, the seed `CLAUDE.md` marked ENTRY, the project addendum, workflow additions, each composed constraint, in composition order — beside a Read (Markdown through `markdown.js`'s `md()`, frontmatter shown literally) / Raw / Composed viewer with a copy button; Composed is the exact prompt with the selected file's section marked. Harness / Runtime is one row per activity, each `modelResolveReport` (`src/v2/model-resolve-report.ts`, the same builder `forge model resolve --json` prints) carried verbatim as `resolve`, then the container (mounts and modes, auth volume, skill mounts, idle timeout, network), with the raw `settings.json` and runtime YAML in a closed `<details>` naming the edit paths. Skills rows carry the `SKILL.md` frontmatter description and a source badge (Forge bundled, project, host path), the optional flag and whether the seed names the skill; "available, not mounted" is empty until FG-797/FG-798. Capabilities holds the routes (moved from Overview), activities, result-contract fields (the protocol's or seed's `## Output schema` block), mount mode and constraints by name. Tools adds effective access (mounts, network, the toolchain from `docker/agent-dev-worker.Dockerfile`, MCP none) beside the declared-not-enforced list. Usage has 1d/7d/30d/all period buttons, by provider and by model with requests; cost only for an API-key provider with a pricing source (none exists: "tokens only"). Overview has a Latest task card (FG-824 task token, relative time) and Skills chips. No role tab shows a status pill of the role's own.
- **Read-only, two GETs, nothing shelled.** `GET /api/roles` and `GET /api/roles/:role` (`src/roles.ts`) read the seed dir, the generation (protocols, runtimes, workflows, compiled routing policy), the model policy and the store. ## RACI authoring (FG-834)

- **The CLI's gate, confirmed from here.** `POST /api/raci/propose` and `POST /api/raci/apply` are `ACTION_ROUTES` rows (`raci-mutation.ts`). The candidate RACI travels as text in the JSON body (at most 256 KiB), is written to a per-request scratch file under `$FORGE_HOME/dashboard/raci-candidates/` (never the project) and removed when the child exits; only that path reaches argv. `--project` is the registry's checkout for `projectKey`, never a caller path. No `--force`, and no route to `forge route compile` or `forge raci validate`.
- **Apply is refused by name before it spawns**: `rationale_required` (blank), `rationale_invalid` (over 2000 characters, or beginning with `-`), `confirm_key_mismatch` (`confirmKey` must equal the project key), `candidate_changed` (`proposedSha256` is not sha256 of the candidate), `candidate_not_proposed` (no green propose of those bytes for that checkout in the last 15 minutes; the window is in memory and an applied proposal is spent). The CLI then re-runs the gate, writes the override, recompiles the policy and appends the audit line with `actor: "dashboard"`, `source: "dashboard"`, the `rationale` verbatim and `candidate_sha256` (its `candidate` path is the removed scratch file, so the sha is the durable identity); its refusal comes back as `refusal: "gate_failed"` with the findings.
- **`GET /api/raci?project=<key>`** is the editor's read: the effective source (project override, else the host default), the host default itself (`host`, for Reset to host default), the `/api/governance` panel, and the checkout's `.forge/raci-audit.log` tail — read by `src/raci-audit.ts`, the ONE audit reader `/api/governance`'s `recorded` section also uses (FG-840: the scoped checkout's log, the host log only with no project in scope, `source`/`path` naming which). The same reader refuses (`refused: "outside_checkout_forge"`, entries withheld) a checkout whose `.forge` or `raci-audit.log` realpaths outside `<checkout>/.forge` — a symlinked escape is never followed — and normalizes every entry's attribution to one field, `actor`: a line written as `by` (model-policy's own audit line, below) comes back renamed.
- **Attribution is a claim, not a proof (FG-840 AC 4).** `--by`/`--source` are recorded exactly as the caller passed them, and any local forge caller can pass them, so no RECORDED row asserts a bound identity. `claimedAttribution(actor, source)` (`client/raci-editor-state.js`) renders `<actor> (claimed)` (`<actor> (claimed) via <source> (claimed)` when the source differs), falls back to `<source> (claimed)` alone when no actor was recorded, and returns `null` — never a synthesized value — when neither was; `auditRows` (same file) and `policyAuditRows` (`client/models-editor-state.js`) both compute it this way, so Routing and Models never disagree. `AttributionCell` (`client/governance.js`) is the one Who-cell renderer both `RecordedAudit` and `RecordedTable` (`client/models-editor-view.js`) use, rendering a faint "unattributed" for the `null` case; each panel always appends one `AttributionClaimCaption` (`ATTRIBUTION_CLAIM_CAPTION`, `data-testid="attribution-claim"`), even with no rows. No token binding, by operator decision — see the FORGE-DEC-037 addendum.
- **The Edit RACI mode (part 2).** `client/raci-editor-view.js` renders Setup › Routing (`RoutingView`, wrapping `governance.js`'s read-only `GovernanceView`) with an Edit RACI button on the SOURCE row, enabled only with a project checkout in scope. `#routing?mode=edit` (`ROUTES.routing.params`, `mode` closed to `edit`) opens a real `<textarea>` with line numbers, section chips, and the EFFECTIVE (DRY-RUN) table beside it. `client/raci-editor-state.js` is the pure machine (unit-tested in `src/fg834-raci-editor.test.ts`): editing → proposed (bound to the exact text the server answered green for, and its `candidateSha256`) → applied → view; any edit supersedes the proposal and disables Apply; Apply also needs the key typed exactly (no trim/case folding) and a non-blank rationale. Dry-runs are `POST /api/raci/propose` of the draft (`createDryRunner`: 400 ms debounce, the in-flight request aborted by a newer edit, only the newest answer lands, a `503` busy answer retried); findings carry no line, so `locateFinding` places them on the route block's field line (else its header). The effective table is the propose JSON's `candidateRoutes` tagged against `/api/governance`'s routes in force. States render through the FG-824 `raci` vocabulary in `status-tokens.js`. Nothing is stored in the browser — a reload reopens edit mode on the starting candidate. `browser-tests/fg834-raci-editor.test.ts` drives it against the real server and CLI.

- **Keyboard.** The sideways scroller is `tabindex="0"` with a label; lanes and cards follow in DOM order. A key pressed on a button inside a queued card belongs to that button, not to the card's grab/reorder handler.

## Conventions specific to the dashboard

- **No build step.** `tsx` runs the server directly. Browser JS is plain ES modules, no bundler.
- **Fixture ports are process-wide.** Prefer `server.listen(0)` and derive the base URL from the bound address. A fixture that genuinely needs a fixed `PORT`/`TEST_PORT` literal must be unique across both `src/**/*.test.ts` and `browser-tests/*.test.ts`; `src/util/fg839-browser-tier-content-guard.test.ts` enforces this and names collisions.
- **Fixture conventions.** The server binds asynchronously during module import, so a fixture must await the shared `awaitDashboardReady(base, { timeoutMs })` helper (`dashboard/src/test-support/await-dashboard-ready.ts`) before any case runs, rather than issuing its first request straight after import — under the parallel tier's load the request can beat the bind even on a unique port and fail with `fetch failed`. Also set `FORGE_DASHBOARD_REMOTE=0` in the fixture's env so the optional remote-board listener never adds its own port error to the run. `src/util/fg839-browser-tier-content-guard.test.ts` enforces both halves: it refuses, by file name, a dashboard-server fixture that requests a route before the awaited probe or that omits the opt-out. A fixture that calls the CLI synchronously between requests must use `fixtureFetch` from `src/test-support/fixture-fetch.ts`, not bare `fetch`: server and client share an event loop, and a synchronous CLI call can block it past the server's keep-alive timeout, leaving the next request to reuse a destroyed idle socket (`read ECONNRESET`). `fixtureFetch` sends `Connection: close`; `awaitDashboardReady` uses it too, so the readiness probe never leaves a pooled socket behind.
- **Read-only DB open.** `queries.ts` opens with `{ readonly: true }`. WAL mode means we don't block forge writers.
- **Mutations shell out.** `server.ts` owns a closed set of eighteen mutating routes: the four queue-planning POSTs (`/api/queue/enqueue|dequeue|rank|reorder`, each shelling one `forge queue` verb via `queue-mutation.ts`), `POST /api/projects/classify` (shelling `forge projects classify`), and the three task actions (`/api/task/:id/gate|retry|recover-re-drive`, the `ACTION_ROUTES` registry in `action-mutation.ts`, shelling `forge gate <id> <decision> --rationale <text> --decided-by dashboard`, `forge retry <id>` and `forge recover <id> --re-drive`), and the three attention-row actions (`/api/attention/:itemKey/dismiss|snooze|undismiss`, the same registry, shelling `forge attention dismiss|snooze|undismiss <item-key> --actor dashboard`), and the two RACI actions (`/api/raci/propose|apply`, the same registry, shelling `forge raci propose <scratch> --project <checkout> --json` and `forge raci apply <scratch> --project <checkout> --confirm --by dashboard --source dashboard --rationale <text> --json` (the rationale is one argv element, never interpolated) over a FORGE_HOME scratch copy of the candidate text), and the two model-policy actions (`/api/model-policy/propose|apply`, the same registry, shelling `forge model policy propose <scratch> [--project <checkout>] --json` and `forge model policy apply <scratch> [--project <checkout>] --confirm --by dashboard --source dashboard --rationale <text> --json`, never `--allow-undispatchable`), and the two attribution actions (`/api/ai-attribution/project|host`, the same registry, shelling `forge config set ai-attribution <suppress|allow> --project <checkout> --actor dashboard` or `forge config unset ai-attribution --project <checkout> --actor dashboard` for the project, and `forge config set ai-attribution <suppress|allow> --host --actor dashboard` for the host default), and the ticket-body edit (`/api/backlog/:id/edit`, the same registry, shelling `forge backlog edit <id> --body - [--base-revision <n>]` in the registry's checkout with the body text delivered on the child's stdin — never argv — bounded at `MAX_TICKET_BODY_BYTES` (64 KiB), the actor passed as `FORGE_ACTOR=dashboard` and recorded on the CLI's `backlog.ticket_edited` event; DB-mode projects only; the response carries the new revision and the re-run readiness verdict; a moved `baseRevision` refuses `409 revision_moved` rather than clobbering a concurrent edit). Every other method is refused. There are no next, cancel or dispatcher routes, and no route passes `--force`. All of them share `mutation-guards.ts` (loopback bind unless `FORGE_DASHBOARD_ALLOW_REMOTE_MUTATIONS=1`, same-origin, `application/json`, argv array with leading-dash rejection); the actor is recorded server-side. This keeps forge's CLI as the single entry point for state changes (FORGE-DEC-015). The opt-in Remote Board (`src/remote/server.ts`) is a separate loopback listener with its own single `POST /api/plan` route, which delegates to an in-process store authority rather than shelling out.
- **Cross-project by design.** The dashboard intentionally shows runs across every project on the host (the cross-project survey surface). It does NOT apply `forge status`'s workspace filter.
- **The server is single-threaded — a synchronous serving path starves EVERY route (FG-742).** All routes share one Node event loop. A route that blocks it synchronously (the standing example: `/api/in-flight`'s FG-290 reconcile annotation `execFileSync`s `docker inspect` per running container — BD-13's recorded exception) blocks a *concurrently polled sibling* too, no matter how cheap that sibling's own query is. FG-742 was exactly this: `/api/current-activity` reads persisted state in milliseconds and shells out to nothing, yet it aborted at its 8s client deadline because it queued behind a slow/hung `docker inspect` fan-out. The contract for any serving path that shells out or does unbounded synchronous work: **bound how long it can hold the loop.** The docker probe is bounded by a per-inspect timeout (`RECONCILE_PROBE_TIMEOUT_MS`) and a per-request fan-out budget (`RECONCILE_FANOUT_BUDGET_MS`, wired via `budgetedLivenessProbe` at the `/api/in-flight` route), which caps the worst-case shared-thread stall to ~4.5s regardless of container count or daemon health — comfortably inside the current-activity deadline. Adding a new route that shells out without such a bound reintroduces this whole failure class. Regression: `src/fg742-current-activity-availability.integration.test.ts`.
