# dashboard

The forge dashboard workspace. Read-only view of `~/.forge/forge.db` plus an HTTP server that serves agent results as markdown cards. Shells out to `forge` for its closed set of mutations (the four `forge queue` verbs, `forge projects classify`, the three task actions — `forge gate`, `forge retry` and `forge recover --re-drive` — and the three attention-row actions, `forge attention dismiss|snooze|undismiss`, and the two RACI actions, `forge raci propose|apply`, and the two model-policy actions, `forge model policy propose|apply`) — never writes the DB directly. Next, cancel and dispatcher arming stay CLI-only.

## Layout

- `src/server.ts` — HTTP server (~1,000 LoC). Routes the read API, the closed set of mutating POSTs, and serves the shell.
- `src/queue-mutation.ts`, `src/action-mutation.ts` — the two closed mutation registries (queue planning; task, attention-row and RACI actions, FG-822/FG-823/FG-834); `src/raci-mutation.ts` — the RACI rows' body, proposal window, scratch candidate and `GET /api/raci` read model; `src/model-policy-mutation.ts` — the same for the model-policy rows and `GET /api/model-policy` (FG-835); `src/mutation-guards.ts` — the guards and the `forge` child all share.
- `src/roles.ts` — the Roles surface (FG-817): `GET /api/roles` and `GET /api/roles/:role`, assembled from the installed seeds, the seed generation, the model policy and `queries.ts`'s role reads; the pure seed derivations live in core's `src/v2/role-surface.ts`.
- `src/queries.ts` — `better-sqlite3` reads against `~/.forge/forge.db`. Row types imported from `@forge/types` (forge's `src/types/index.ts`); schema drift surfaces as a TypeScript error here.
- `src/shell.ts` — the HTML shell + CSS (template literals).
- `client/main.js`, `client/renderers.js` — browser JS, served as static files (no build, no bundling).
- `client/backlog.js` — read-only backlog view (`#backlog[/<ticketId>]`); mirrors `/api/backlog`. No writes. Its type/status filter state, hash and "N of M tickets" count are pure helpers in `client/backlog-state.js` (FG-832). It renders tickets only; session-handoff notes are the Notes view's (FG-830).
- `client/ops-window-state.js` — the Ops runtime window and summary since: hash state, the per-metric load reducers and the abortable, budgeted reader (FG-836). No DOM, fetch and timers injectable; unit-tested in `src/fg836-ops-loading.test.ts`.
- `client/notes-render.js`, `client/notes-view.js` — the Notes view (FG-830): `#notes` lists one row per checkout with a note, and `#notes/<checkout>` is that checkout's note page. Both read `/api/backlog`'s `notesByCheckout`; the pure row rules (session date, preview, order, primary) are in `notes-render.js`.
- `client/view-routing.js` — the closed `ROUTES` table and the only hash parser/writer (FG-820).
- `client/governance.js` — the read-only Routing workbench (SOURCE / DERIVED / EFFECTIVE / RECORDED); `client/raci-editor-view.js`, `client/raci-editor-state.js` — its Edit RACI mode (FG-834; see RACI authoring below).
- `client/nav-render.js`, `client/nav-view.js` — the left-column navigation, the narrow-screen bottom bar and drawer (FG-820).
- The cockpit object pages (FG-821), each a pure `*-render.js` (unit-tested, no DOM) beside its `*-view.js`:
  - `client/runs-index-render.js`, `client/runs-index-view.js` — the run index (`#runs[?scope&status=]`) and the Runs badge.
  - `client/run-page-view.js` — the run page (`#run/<runId>[/map|/evidence]`); `client/run-map.js` draws its map tab.
  - `client/task-page-view.js` — the task page (`#task/<taskId>`) and its Explain page (`#task/<taskId>/explain`, body from `client/run-explain-panel.js`'s `ExplainContent`).
  - `client/ticket-page-view.js` — the ticket page (`#backlog/<ticketId>`); `ReviewPage` in `client/reviews.js` is a review by id (`#reviews/<reviewId>`).
  - `client/roles-index-render.js`, `client/roles-index-view.js` — the Roles list (`#roles`, FG-817; sortable headers and the pure `sortRoles` comparator, FG-828).
  - `client/role-page-render.js`, `client/role-page-view.js` — a role page (`#roles/<role>[/<tab>]`, FG-817).
  - `client/role-glyph.js`, `client/role-glyph-view.js` — the role glyph tile (FG-829): the family colour table, the glyph map, `roleFamily`/`roleTile` (pure, an SVG string) and the `RoleTile` Preact element drawn from the same parts.
  - `client/breadcrumbs-render.js` — trails and Escape-to-parent; `client/screen-header-render.js` — the screen contract (object pages' live lines, list views' `LIST_HEADERS`); `client/info-tip.js` — the list-view info tip (FG-838); `client/object-page-view.js` — the shared head, tabs and Escape handling.
- `client/checkout-label.js` — the one checkout label rule (FG-831): `checkoutLabel`, `checkoutLabelForDir`, `checkoutOptions`.
- `client/status-tokens.js` — the one status vocabulary (FG-824); `client/format.js` — the one formatter module (FG-824; it absorbed `duration.js`).
- `client/recovery-card-render.js`, `client/recovery-card-view.js` — the task page's recovery card (FG-824).
- `design/` — Pencil design corpus (`dashboard.pen` + PNG exports).

## Run

From the forge repo root:

```bash
./bin/forge-dev dashboard start    # boots tsx src/server.ts in this dir on port 8024
npm --workspace=dashboard typecheck
```

`./bin/forge-dev dashboard start` is the source-checkout entry. But the dashboard is now bundled into the promoted release as a mandatory asset (FG-580), so `forge dashboard` also runs from a promoted release — resolution is release-owned (it flows from `assetRoot()`, the executing release or the dev checkout, never the invocation cwd), and the FG-569 release-mode refusal is retired. The bundled UI boots offline: its client libs are vendored in-closure and served under a `script-src 'self'` CSP, so no CDN-executed JS is fetched (provider/data APIs may still need network). A torn/incomplete release — a missing dashboard file, vendored client lib, or dashboard-relevant dep — still fails named and nonzero (`assertDashboardClosure`) rather than falling back to a source checkout.

## Navigation (FG-820)

The plan is `docs/research/dashboard-information-architecture.md`. The 13-button tab strip is gone; there is no flag or twin keeping it alive.

- **Left column.** A scope control at the top ("All projects", a project, or project › checkout — a filter, never a switcher), then five groups under plain, non-collapsible headings, then the last-poll clock. Now: Home, Activity. Plan: Backlog, Notes, Queue, Campaigns. Evidence: Runs, Reviews, Shipping. Setup: Roles, Routing, Config, Projects. Health: Usage, Ops. Runs is the run index (FG-821); Roles is the Roles list (FG-817).
- **Keyboard (FG-692).** Every item is an `<a href="#…">`; group headings are not controls; `aria-current="page"` marks the current item; a "Skip to content" link comes first and the tab order is column → content. An object page highlights its parent (a run page highlights Runs).
- **Below 720px** (the nav breakpoint; 520/600/640 stay content breakpoints) the column is replaced by a fixed, safe-area-padded bottom bar — Home, Runs, Queue, Backlog, More. More opens a drawer holding the full column: a modal dialog that traps focus, closes on Escape, and returns focus to More.
- **`ROUTES` (`client/view-routing.js`).** A closed table: each view names its group (`now | plan | evidence | setup | health`), path pattern, scope requirement (`none | optional | project | checkout`) and legacy aliases. `parseHash` returns view, object id, tab and scope; unknown parameter keys are dropped; an unknown view lands on Home with a one-line "No view named …" notice. **The group is derived from the view, never read from the hash** — a `group=` parameter or a group-shaped leading segment (`#plan/queue`) is dropped and the URL rewritten with `history.replaceState`.
- **Aliases.** `#governance` → `#routing`, `#control-plane` → `#config`, `#run-map/<id>` → `#run/<id>` (the run page's default `map` tab; FG-821 — keep this alias permanently, saved and emitted `#run-map/<id>` links must resolve forever). A bare object hash (`#run-map`, `#run`, `#task`) lands on the run index with an "open a run from the run index" prompt. Every alias is rewritten to its canonical hash in place.
- **Object tabs.** Object routes name their tabs in `ROUTES` (`run`: `map`, `evidence`; `task`: `detail`, `explain`; `roles`: `overview`, `instructions`, `harness`, `skills`, `capabilities`, `tools`, `secrets`, `tasks`, `receipts`, `usage`). The first is the default and is omitted from the canonical hash; an unknown tab falls back to it. A route may map a retired tab name onto its successor (`tabAliases`: roles' `configuration` → `harness`), so an old link lands on the renamed tab and is canonicalized to it. `notes` takes an optional checkout segment, `#notes/<URI-encoded checkout directory>`, and has no tabs. A route may also own extra hash parameters (`params`: the run index's `status=`, the Roles list's `sort=`/`dir=`, the Backlog's `type=`/`status=`), optionally closed to a vocabulary (`paramValues`: an unknown value is dropped from the canonical hash); a route's params belong to its list, so an object hash (`#roles/<role>`) carries none; every other key is still dropped.
- **Scope lives in the hash.** List views carry `?project=<projectKey>[&checkout=<URI-encoded projectDir>]`, mapped one-to-one onto the server's `?projectKey=`/`?projectDir=`. A scope change rewrites the hash with `replaceState`; moving between list views keeps it; scope-less views (`#projects`, `#roles`) and object hashes (`#run-map/<id>`) carry none and leave the scope in hand untouched. Never `localStorage`/`sessionStorage`. The Remote Board must not adopt this scheme — the checkout parameter puts a host path in the URL.
- **No client-computed counts.** There are two nav badges. Home's is the attention envelope's server-computed `counts` (`src/v2/attention-inbox.ts`, the same derivation `forge attention list` prints): `counts.open`, danger-toned when `counts.high > 0`, a partial marker when `degraded` is non-empty, "?" when the read failed or carries no valid `counts`, hidden only when `empty: true`, capped at "99+". Never `items.length`, a per-view tally, a filtered-list count, read/unread state, or anything stored. The inbox is read on every view so the badge is live everywhere. Runs' is `GET /api/runs`'s server-computed `activeCount` (the derivation `forge runs query --status active` prints; `runs-index-render.js`'s `runsBadge`): an informational live count, never danger-toned, "?" when the read failed or carries no integer `activeCount`, hidden at 0, capped at "99+". It is read at 30s on every view, and the run index hands up its own first-page response so on `#runs` the badge is the list's own answer. Never `runs.length` or a count of a filtered or paged list.

## Object pages (FG-821)

- **No modal overlays for task detail or Explain.** Every entry point — feed cards, inbox rows, in-flight and orchestrator rows, current-activity rows, run map nodes — is (or navigates to) a link: a task row opens `#task/<taskId>`, a run-map node opens `#task/<taskId>/explain`, an inbox run row opens `#run/<runId>`. The task page and its Explain page link to each other as tabs.
- **Object pages read by global id, unscoped.** The run, task, Explain and review pages ignore the scope in hand, so an inbox click and a pasted link read the same object. The ticket page is the exception: ticket ids are per project, so `GET /api/backlog/:id/runs` and the ticket's fields are read with the list scope.
- **Breadcrumbs on object pages only, built from the payload, never from history:** Project › [Ticket ›] Run › Task › Explain. Every crumb but the last is a link; Project resolves to `#runs?project=<key>` (matched from the payload's `projectDir` against `/api/projects`, or the backlog's `ticketsProjectKey`). The ticket crumb comes from a `links.ticketId`: `GET /api/task/:id`'s for the task page, `GET /api/run/:id/evidence`'s for the run page. List views show group and title instead.
- **Screen headers: title + live state only (FG-838).** A list view renders its title and, where one exists, a live count (Runs' "N runs are active") — nothing else. Its contract (what is happening, whether it needs you, what to do, the CLI verb) is the `LIST_HEADERS` entry shown in the info tip beside the title: a 20px "?" button in the faint token, a hover/focus tooltip, and a click/Enter/Space popover (a dialog that takes focus; Escape or a click outside closes it, focus returns to the "?") with the verb as code and a Copy button. One `InfoTip` in `main.js` serves every list view; add a view's copy to `LIST_HEADERS`, never per-view markup. "Source: …" captions go in a footer under the content, not between the title and the content.
- **Screen line.** An object page states what is happening, whether it needs you, and what to do in one line, naming the next CLI verb where one applies — live facts only: a sentence that reads the same for every object is filler and does not belong in it. Object-page copy is read from the payload — the task's status and failure kind, and `GET /api/attention-inbox?runId=`'s `reason`/`requestedAction` (for a failed task that is the retry policy's advice). A task at `awaiting_gate` names `forge gate <id>`; a failed one `forge show <id>`.
- **Escape on an object page navigates to its parent:** Explain → task → run → `#runs`; ticket → `#backlog`; a note → `#notes` (scope kept); review → `#reviews`; a role page (any tab) → `#roles`. A key typed into a field, or an open modal (the nav drawer), is left alone.
- **Run evidence** (the `evidence` tab) is one `GET /api/run/:id/evidence` read per run visit — the server's own union of the run's reviews, launches and host verifications by run id (`queries.ts`'s `runEvidence`), not a client-side fold over each task's `links`. Reviews link to `#reviews/<id>`, launches to `/api/launches/<id>` and its `/log`, host verifications to the run's first task's Explain page (which shows the evidence).

## Roles (FG-817)

- **Every installed seed is an object.** `#roles` lists each directory under `$FORGE_HOME/agents` that carries a `CLAUDE.md`: its first paragraph, default activity (`defaultActivityForRole`), the profile/model/effort model policy resolves for that activity (`resolveModel` under the current seed generation), its `/project` mount and its last task. `#roles/<role>/<tab>` is a role page, deep-linkable, with `overview` the default (omitted from the canonical hash) and an unknown tab falling back to it. Tabs use the FG-821 tablist; the trail is Roles › `<role>` › `<tab>`. The list's headers (Role, Default activity, Resolved profile, Mount, Last task) are buttons that sort the fetched payload client-side (FG-828): first click ascending, second descending, `aria-sort` and a glyph on the active column; missing values (no default activity, a legacy or unresolved profile, never ran) sort last in both directions, ties by role name ascending, and Last task sorts on the ISO timestamp. The sort rides the hash as `#roles?sort=role|activity|profile|mount|lastTask&dir=asc|desc` — only a header click writes it (the nav link stays `#roles`), and an unknown value falls back to role ascending.
- **Ten tabs, each captioned with its source** (`source` on each tab's payload, printed as a "Source: …" footer under the tab's content, FG-838): overview, instructions, harness, skills, capabilities, tools, secrets, tasks, receipts, usage. Instructions is `composeSystemPrompt`'s own output for `forge invoke <role>` with no project anchored (so no project addendum appears; the segmenter marks one when present), shown as marked sections — protocol, role seed, addendum, workflow additions, each constraint, framing — that concatenate to the exact bytes, with the sha256 of those bytes. A role dispatch would refuse (a covered role with no current protocol) shows the refusal instead. Secrets is the literal "none: containers receive no project secrets"; tools lists `settings.json`'s `tools`, flagged declared-not-enforced, MCP none; usage names ceilings as a future ticket.
- **FG-827: the tabs and their sources.** Instructions (`client/instructions-panel-render.js` / `-view.js`) is a Files panel over `instructions.files[]` — protocol, the seed `CLAUDE.md` marked ENTRY, the project addendum, workflow additions, each composed constraint, in composition order — beside a Read (Markdown through `markdown.js`'s `md()`, frontmatter shown literally) / Raw / Composed viewer with a copy button; Composed is the exact prompt with the selected file's section marked. Harness / Runtime is one row per activity, each `modelResolveReport` (`src/v2/model-resolve-report.ts`, the same builder `forge model resolve --json` prints) carried verbatim as `resolve`, then the container (mounts and modes, auth volume, skill mounts, idle timeout, network), with the raw `settings.json` and runtime YAML in a closed `<details>` naming the edit paths. Skills rows carry the `SKILL.md` frontmatter description and a source badge (Forge bundled, project, host path), the optional flag and whether the seed names the skill; "available, not mounted" is empty until FG-797/FG-798. Capabilities holds the routes (moved from Overview), activities, result-contract fields (the protocol's or seed's `## Output schema` block), mount mode and constraints by name. Tools adds effective access (mounts, network, the toolchain from `docker/agent-dev-worker.Dockerfile`, MCP none) beside the declared-not-enforced list. Usage has 1d/7d/30d/all period buttons, by provider and by model with requests; cost only for an API-key provider with a pricing source (none exists: "tokens only"). Overview has a Latest task card (FG-824 task token, relative time) and Skills chips. No role tab shows a status pill of the role's own.
- **Read-only, two GETs, nothing shelled.** `GET /api/roles` and `GET /api/roles/:role` (`src/roles.ts`) read the seed dir, the generation (protocols, runtimes, workflows, compiled routing policy), the model policy and the store. There is no POST — a seed changes only through `forge upgrade` — and neither route runs a subprocess or makes an outbound call (`src/fg817-roles-routes.integration.test.ts` guards it) — except that `?project=<key>` on the role route resolves the key through `projectsForDashboard()`, the same registry read (and bounded `git` evidence probe) `/api/queue` pays, so the Instructions tab can compose with that project's addendum. Without it the composition is host-only and the caption says so. A seed without `settings.json` is `present: false`, never a 500; an unknown role is a 404.
- **FG-829: role glyph tiles — colour by family, glyph by role.** `client/role-glyph.js` holds `ROLE_FAMILIES` (red `#e0574f`, build `#3b6cff`, test `#39b86f`, review `#e59a2b`, research `#8e5cff`, plan `#26bfb1`, author `#f5b400`, neutral `#9a9aa3` — the FG-824 neutral token), `ROLE_FAMILY_OF` (role → family; every `red-*` is red and nothing else is), `ROLE_GLYPHS` (role → glyph in `GLYPHS`, 24-unit line icons) and `roleTile(role, size)`. The tile is inline SVG — a rounded square, family colour at 13% fill and a 1px 33% border, the glyph stroked in the colour — 20px beside the name in the Roles list, In flight rows (Home and Activity) and Activity's Recent agent outputs rows, 36px beside a role page's title; views render it through `RoleTile` (`role-glyph-view.js`) rather than `dangerouslySetInnerHTML` (FG-643 R2). Its only CSS is `.role-tile`/`.role-name`/`.role-title` placement in `src/shell.ts`. Beside a visible name it is `aria-hidden`; `standalone` makes it `role="img"` with an `aria-label`. An unknown role is neutral with the layers glyph, never an error. **A new seed is one line in `ROLE_FAMILY_OF` and one in `ROLE_GLYPHS`** — `src/fg829-role-glyph.test.ts` enumerates `seeds/agents/*` and fails otherwise; `browser-tests/fg829-role-glyphs.test.ts` renders them.

## Task actions (FG-822)

- **Preview first.** `GET /api/task/:id/actions` returns the actions the task admits now (`eligible`: the verb, the exact argv, the policy reason) and the ones it does not (`refused`: the reason and the retry policy's advice), plus whether this bind admits mutations at all. Each POST re-runs the same decision (`previewTaskActions`) before it builds argv, so a refused action is refused by name with its advice.
- **Eligibility.** Gate: only `awaiting_gate`, a rationale for every decision. Retry: only a failed task whose recorded failure kind has a `POLICY` row with `retryable: true` and no advice (`recordedRetryDisposition`, never `retryPolicy()`'s advisory default), and only a runner-stamped workflow step — an ad-hoc retry dispatches its container inside the forge process. Re-drive: only a failed task whose kind `RE_DRIVABLE_FAILURE_KINDS` accepts.
- **Where the buttons live.** The task page's screen line and each Home inbox row whose task has an eligible action (`client/task-actions-view.js`, decisions in `client/task-actions-render.js`). A button is labeled with its verb; clicking it previews the verb (and, for a gate, asks for the rationale) before Confirm; the verb's exit status and output render inline. Buttons are never badge-bearing, and there is no typed-identifier confirmation — nothing here is bulk or irreversible.

## Attention dismiss and snooze (FG-823)

- **Server-side, audited, never in the browser.** Dismiss, Snooze and Undismiss are `ACTION_ROUTES` rows shelling `forge attention dismiss|snooze|undismiss <item-key> --actor dashboard [--until <t>] [--rationale <text>]`. The inbox offers the snooze presets `1h`, `4h`, `1d` (`SNOOZE_PRESETS` in `client/attention-dismiss-render.js`) or a custom ISO instant; the route and the CLI accept any duration — `90m`, `4h`, `1d`, `2w` — or ISO instant up to a year out, both through the same `parseSnoozeUntil`. The CLI writes the `attention_dismissals` row and its `attention.*` event; the client stores no read or dismiss state and never touches `localStorage`.
- **The server excludes, the client never filters.** `GET /api/attention-inbox` already leaves held items out of `items` and `counts` (so the Home badge drops on the next poll) and lists them under `dismissed`, which the "Dismissed" disclosure at the foot of the inbox renders with Undismiss. A dismissal holds until the item's `startedAt` advances past it; a snooze also clears when its instant passes.
- **An all-held inbox still names its count, never the calm copy.** Zero `items` normally reads as `INBOX_EMPTY_LABEL` ("No human action is currently needed"), but held items are still the operator's to act on (Undismiss) — so when `dismissed` is non-empty on an otherwise-empty read, the surface shows `inboxHeldLabel(count)` ("No open items — N held (dismissed or snoozed)") instead (`client/attention-inbox-render.js`).
- **One preview per row.** An inbox row owns which preview is open (`InboxRowControls` in `client/attention-inbox-view.js`): opening the hold preview (`.hold-preview`) closes the task-action preview (`.task-action-preview`) and the other way round; both keep the shared `.action-preview` / `.action-preview-verb` / `.action-confirm` classes. Opening either focuses its first control; Escape closes it and returns focus to its button. The task page's own action preview keeps its FG-822 behavior (no Escape binding there).
- **Order pinning.** A dismissed row leaves the pinned order at once (pinning holds order, not membership); an undismissed row comes back where the server places it, at the next boundary.

## RACI authoring (FG-834)

- **The CLI's gate, confirmed from here.** `POST /api/raci/propose` and `POST /api/raci/apply` are `ACTION_ROUTES` rows (`raci-mutation.ts`). The candidate RACI travels as text in the JSON body (at most 256 KiB), is written to a per-request scratch file under `$FORGE_HOME/dashboard/raci-candidates/` (never the project) and removed when the child exits; only that path reaches argv. `--project` is the registry's checkout for `projectKey`, never a caller path. No `--force`, and no route to `forge route compile` or `forge raci validate`.
- **Apply is refused by name before it spawns**: `rationale_required` (blank), `rationale_invalid` (over 2000 characters, or beginning with `-`), `confirm_key_mismatch` (`confirmKey` must equal the project key), `candidate_changed` (`proposedSha256` is not sha256 of the candidate), `candidate_not_proposed` (no green propose of those bytes for that checkout in the last 15 minutes; the window is in memory and an applied proposal is spent). The CLI then re-runs the gate, writes the override, recompiles the policy and appends the audit line with `actor: "dashboard"`, `source: "dashboard"`, the `rationale` verbatim and `candidate_sha256` (its `candidate` path is the removed scratch file, so the sha is the durable identity); its refusal comes back as `refusal: "gate_failed"` with the findings.
- **`GET /api/raci?project=<key>`** is the editor's read: the effective source (project override, else the host default), the host default itself (`host`, for Reset to host default), the `/api/governance` panel, and the checkout's `.forge/raci-audit.log` tail.
- **The Edit RACI mode (part 2).** `client/raci-editor-view.js` renders Setup › Routing (`RoutingView`, wrapping `governance.js`'s read-only `GovernanceView`) with an Edit RACI button on the SOURCE row, enabled only with a project checkout in scope. `#routing?mode=edit` (`ROUTES.routing.params`, `mode` closed to `edit`) opens a real `<textarea>` with line numbers, section chips, and the EFFECTIVE (DRY-RUN) table beside it. `client/raci-editor-state.js` is the pure machine (unit-tested in `src/fg834-raci-editor.test.ts`): editing → proposed (bound to the exact text the server answered green for, and its `candidateSha256`) → applied → view; any edit supersedes the proposal and disables Apply; Apply also needs the key typed exactly (no trim/case folding) and a non-blank rationale. Dry-runs are `POST /api/raci/propose` of the draft (`createDryRunner`: 400 ms debounce, the in-flight request aborted by a newer edit, only the newest answer lands, a `503` busy answer retried); findings carry no line, so `locateFinding` places them on the route block's field line (else its header). The effective table is the propose JSON's `candidateRoutes` tagged against `/api/governance`'s routes in force. States render through the FG-824 `raci` vocabulary in `status-tokens.js`. Nothing is stored in the browser — a reload reopens edit mode on the starting candidate. `browser-tests/fg834-raci-editor.test.ts` drives it against the real server and CLI.

## Model-policy authoring (FG-835)

- **The same shape as the RACI rows.** `POST /api/model-policy/propose` and `POST /api/model-policy/apply` are `ACTION_ROUTES` rows (`model-policy-mutation.ts`) shelling `forge model policy propose|apply`. The body names ONE target: `projectKey` (the registry's checkout becomes `--project`, never a caller path; `projectDir` only selects among the project's own checkouts) or `target: "host"` (no `--project`: the host `~/.forge/model-policy.yml`). The candidate YAML travels as text (at most 64 KiB), is written to a per-request scratch file under `$FORGE_HOME/dashboard/model-policy-candidates/` and removed when the child exits; only that path reaches argv. Never `--allow-undispatchable` (accepting an undispatchable role stays a terminal decision), never `--force`.
- **Apply is refused by name before it spawns** with the RACI rows' codes: `rationale_required`, `rationale_invalid`, `confirm_key_mismatch` (`confirmKey` must equal the project key, or the literal `host` for the host file), `candidate_changed`, `candidate_not_proposed` (no green propose of those bytes for that target in the last 15 minutes; a host propose never admits a project apply and vice versa). One green propose admits one apply; it is refunded only when the child wrote nothing. The CLI re-runs the gate, keeps a timestamped backup, replaces the file atomically and appends the `model-policy-audit.log` line with `by: "dashboard"`, `source: "dashboard"`, the `rationale` and `candidate_sha256`; its gate refusal comes back as `refusal: "gate_failed"` with the findings.
- **`GET /api/model-policy[?project=<key>]`** is the editor's read: the target file (with its sha256 and the confirm key), the effective source (project override, else host) with its YAML text, the resolution table for every installed role × activity (built by `roles.ts` `harnessActivities`, so it cannot disagree with the Roles Harness tab), the audit tail beside the target (newest first, 20 lines) and the target's `.bak-*` backups (newest first, with sha256 and size). No subprocess.

## Status tokens, formatters, freshness and recovery (FG-824)

- **One status vocabulary.** `client/status-tokens.js` maps each closed store vocabulary — `tasks.status` (`TASK_STATUSES`), `runs.status` (`RUN_STATUSES`), attention kinds (`ATTENTION_ITEM_KINDS`), launch outcomes (`LAUNCH_STATES`, plus the `unobserved` marker), queue claim states (`QUEUE_CLAIM_STATES`) and the orchestrator presentation (`ORCHESTRATOR_PRESENTATIONS`), with ticket status and two markers besides — to `{label, tone, class}`. Every badge, row accent (`toneAccentClass`), run-map colour (`runMapStatusClass`) and timeline marker renders through `statusToken`/`statusClass`/`badgeClass`; a surface with its own domain (campaign status, review disposition, a verification event) maps it to the task status whose token already means the same thing. An unknown value renders its vocabulary's neutral italic fallback labeled `<value> (unrecognized)` — never blank, never the raw string alone. `src/fg824-status-tokens.test.ts` fails when a store member lacks a token or a CSS rule, when the map carries a value the store no longer has, and when any other `client/*.js` spells a status class (`status-*`, `run-status-*`, `inbox-kind-*`, `launch-state-*`, `claim-state-*`, `rm-status-*`, `tone-accent-*`) itself. Adding a store value means adding its token and its `.badge.<class>` rule in the same change.
- **One formatter module.** `client/format.js` formats ids (`shortId`, `idDisplay` — full value in `title`), shas (`shortSha`), durations (`formatDuration`), token counts (`formatTokens`) and timestamps (`formatRelativeTime`, `formatTimestamp`, `formatClock`, `timestampDisplay` — relative text, absolute title); monospace is `MONO_CLASS`. `src/fg824-format.test.ts` fails when another client module slices a sha, calls `toLocale*String`, defines its own `fmt*`/`format*` duration/time/token helper or divides a count for display.
- **Freshness is informational.** A launch row the store last saw `running` shows "unobserved for N min" (`launchFreshness` in `client/current-activity-render.js`) — the payload's own `generatedAt` minus the row's `observedAt`, the server's clock on both sides, suspicious at 15 minutes and critical at 60. It changes neither the row's status nor its membership, and a terminal outcome never carries it. Home's In-flight host-wait rows only ever reach the suspicious band (the server's 30-minute cutoff drops a stale row from Home); the Activity view's launch rows carry the whole range.
- **Recovery card.** `#task/<id>` shows one card when the task is `awaiting_recovery` or failed with an orphan kind (`ORPHAN_FAILURE_KINDS`, checked against core's `ORPHAN_EVIDENCE_KINDS` and every orphan-named failure kind): the failure kind, the newest `task.reconciled` a `forge recover` wrote, and the next verb. It reads the FG-822 preview: an eligible re-drive (or retry) is a button with the same preview → Confirm → inline result flow; otherwise the verb — `forge next <run>` for `awaiting_recovery`, `forge recover <id> --re-drive` for `fanout_wave_orphaned`, `forge show <id>, then forge recover <id>` for `orphaned_needs_finalize`, `forge recover <id>` for every other orphan kind — and the policy's advice. The card never builds a `--force` verb; a bypass appears only in the policy's own advice text. No toast layer exists; nothing toasts state already on screen.

## Checkout labels (FG-831)

- **One label rule.** `client/checkout-label.js` names a checkout as its directory's basename plus just enough parent segments to be unique among the project's checkouts, then ` · <branch>` — `forge · main`, `forge-fg827 · feat/fg-827-roles-second-pass`, `run-1/forge · main`. A checkout whose directory is gone reads ` · missing on disk` in place of a branch. The scope bar, the Projects card rows, Notes rows, ticket chips, the Runs index and Activity's project chip all call `checkoutLabel`/`checkoutLabelForDir`; no view derives a checkout name from `branch` or a basename itself.
- **The scope bar's options** come from `checkoutOptions(project, { showMissing, selected })`: deduplicated by canonical path (the registry already realpaths every checkout that exists, FG-693), the primary checkout first and marked `primary`, then the on-disk checkouts, then the missing ones. A missing checkout is withheld behind a "show N missing" toggle (component state, not the hash) unless it is the current selection. Selecting one never errors — its runs and notes render where they exist.
- **Missing checkouts reach the client.** `presentationRegistry` (`src/queries.ts`) now drops only a project whose every checkout is gone, idle and session-less; a surviving project keeps all its checkouts so the client can count them. The Projects card lists on-disk checkouts (plus a missing one still carrying work or a live session) and counts the rest beside `forge projects prune --missing`. The dashboard never prunes; the verb records the prune in `pruned_checkouts`, and `listProjects` stops offering a pruned checkout while its directory stays gone.

## Notes view (FG-830)

- **Notes moved out of the Backlog.** Session-handoff notes (`backlog/notes.md` per checkout, `forge backlog notes`) are not backlog state. `#notes` sits under Plan after Backlog, with project-optional scope. With no project selected it asks for one. The Backlog page starts at its tickets.
- **Rows.** There is one row per checkout with a non-empty note, labeled by `checkoutLabelForDir` (FG-831). Each row shows the session date through `format.js`'s relative time and a one-line preview, and the project's primary checkout is marked `primary`. Rows sort newest session first, with unknown dates last. The session date is the note's `Last session ended YYYY-MM-DD` line, else `notes.md`'s mtime (`modifiedAt` on each `notesByCheckout` entry), else "session date unknown".
- **Note page.** `#notes/<checkout>` renders the full note with `md(notes, { html: "text" })`, so raw HTML shows as literal text. The trail is Project › Notes › checkout, and Escape goes to `#notes` with the scope kept.
- **No new route.** The view reads the existing `GET /api/backlog` payload; `main.js` polls it on both `#backlog` and `#notes`. Nothing here writes.

## Backlog filter (FG-832)

- **The Backlog opens on every type, active only.** Type All and status Active are the defaults and render selected (`aria-pressed`), never as "no filter"; the controls are two labelled button groups. The filter rides the hash as `#backlog?type=epic|story|idea&status=all|active|blocked|deferred|done` — a button writes it, a missing `type` means all, a missing `status` means active, the canonical hash omits both defaults (`#backlog?status=active` canonicalizes to `#backlog`), and an unknown value is dropped silently. `#backlog/<id>` carries none. The count line reads "N of M tickets" for the current filter and search. Filtering stays client-side over the one `GET /api/backlog` read; the left column has no Backlog badge.
- **Pure helpers, no DOM.** `client/backlog-state.js` holds `backlogFilterState`, `backlogFilterHash`, `filterBacklogTickets` and `backlogCountLabel` — unit-tested without a browser, same shape as `view-routing.js`.

## Ops windows (FG-836)

- **The window is hash state.** `#ops?window=1d|30d|90d|all` (`ROUTES.ops.params`, alongside `since`). 7d is the default and is omitted from the canonical hash, and an unknown value is dropped silently. A window button writes the hash; `main.js` derives the window from `route.params`.
- **Loading is explicit, and the previous data stays.** `client/ops-window-state.js` holds one load per metric, `{ data, window, error, pending }`, where `window` is the window the data came from. While a read for another window is in flight, the buttons are disabled, the chart is dimmed under a "loading <w>…" line (FG-824 `tone-accent-info`), and the label beside the buttons reads "showing <data window>"; the pressed button follows the data too. A background refresh of the window on screen is silent.
- **Abort and budget.** `createWindowedReader` aborts its in-flight read when a newer one starts, and also after `OPS_FETCH_BUDGET_MS` (10s). A timeout, an HTTP error or a network error is shown inline with its reason and the window it concerns; the kept series stays. A superseded read never writes. A scope change still calls `reset()` and drops both metrics to loading (FG-699).
- **The summary's since is the same shape.** `#ops?since=30d|all` (7d the omitted default) is the `since` for `GET /api/ops`, read through its own `createWindowedReader` ("ops summary"). `runtimeWindowHash` and `opsSinceHash` each keep the other param, so `#ops?since=all&window=90d` round-trips. The summary shows "showing <w>" beside its buttons, "in <w>" on each count, and the same loading line, dimming (`.ops-summary-body-loading`) and inline failure as the chart. It is not reset on a scope change, as before. Home's summary stays at a fixed 30d and is not hash state.

## Conventions specific to the dashboard

- **No build step.** `tsx` runs the server directly. Browser JS is plain ES modules, no bundler.
- **Read-only DB open.** `queries.ts` opens with `{ readonly: true }`. WAL mode means we don't block forge writers.
- **Mutations shell out.** `server.ts` owns a closed set of fifteen mutating routes: the four queue-planning POSTs (`/api/queue/enqueue|dequeue|rank|reorder`, each shelling one `forge queue` verb via `queue-mutation.ts`), `POST /api/projects/classify` (shelling `forge projects classify`), and the three task actions (`/api/task/:id/gate|retry|recover-re-drive`, the `ACTION_ROUTES` registry in `action-mutation.ts`, shelling `forge gate <id> <decision> --rationale <text> --decided-by dashboard`, `forge retry <id>` and `forge recover <id> --re-drive`), and the three attention-row actions (`/api/attention/:itemKey/dismiss|snooze|undismiss`, the same registry, shelling `forge attention dismiss|snooze|undismiss <item-key> --actor dashboard`), and the two RACI actions (`/api/raci/propose|apply`, the same registry, shelling `forge raci propose <scratch> --project <checkout> --json` and `forge raci apply <scratch> --project <checkout> --confirm --by dashboard --source dashboard --rationale <text> --json` (the rationale is one argv element, never interpolated) over a FORGE_HOME scratch copy of the candidate text), and the two model-policy actions (`/api/model-policy/propose|apply`, the same registry, shelling `forge model policy propose <scratch> [--project <checkout>] --json` and `forge model policy apply <scratch> [--project <checkout>] --confirm --by dashboard --source dashboard --rationale <text> --json`, never `--allow-undispatchable`). Every other method is refused. There are no next, cancel or dispatcher routes, and no route passes `--force`. All of them share `mutation-guards.ts` (loopback bind unless `FORGE_DASHBOARD_ALLOW_REMOTE_MUTATIONS=1`, same-origin, `application/json`, argv array with leading-dash rejection); the actor is recorded server-side. This keeps forge's CLI as the single entry point for state changes (FORGE-DEC-015). The opt-in Remote Board (`src/remote/server.ts`) is a separate loopback listener with its own single `POST /api/plan` route, which delegates to an in-process store authority rather than shelling out.
- **Cross-project by design.** The dashboard intentionally shows runs across every project on the host (the cross-project survey surface). It does NOT apply `forge status`'s workspace filter.
- **The server is single-threaded — a synchronous serving path starves EVERY route (FG-742).** All routes share one Node event loop. A route that blocks it synchronously (the standing example: `/api/in-flight`'s FG-290 reconcile annotation `execFileSync`s `docker inspect` per running container — BD-13's recorded exception) blocks a *concurrently polled sibling* too, no matter how cheap that sibling's own query is. FG-742 was exactly this: `/api/current-activity` reads persisted state in milliseconds and shells out to nothing, yet it aborted at its 8s client deadline because it queued behind a slow/hung `docker inspect` fan-out. The contract for any serving path that shells out or does unbounded synchronous work: **bound how long it can hold the loop.** The docker probe is bounded by a per-inspect timeout (`RECONCILE_PROBE_TIMEOUT_MS`) and a per-request fan-out budget (`RECONCILE_FANOUT_BUDGET_MS`, wired via `budgetedLivenessProbe` at the `/api/in-flight` route), which caps the worst-case shared-thread stall to ~4.5s regardless of container count or daemon health — comfortably inside the current-activity deadline. Adding a new route that shells out without such a bound reintroduces this whole failure class. Regression: `src/fg742-current-activity-availability.integration.test.ts`.
