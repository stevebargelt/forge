# forge-dashboard

Activity feed + agent-output inbox for forge runs across all projects on the host. Lives as a workspace package inside the forge monorepo.

The dashboard is **bundled into the promoted release** (FG-580): its runtime source, static client assets, vendored client libs (offline boot — no CDN-executed JS), and dashboard-relevant deps all ship in-closure, so `forge dashboard start` runs from the stable `forge`. A torn or incomplete release fails named and nonzero rather than pretending to run.

```bash
forge dashboard start                        # boots http://127.0.0.1:8024 from the release
forge dashboard start --port 8025            # custom port

# during development, run it from a source checkout instead:
cd ~/code/forge
./bin/forge-dev dashboard start
```

Reads `~/.forge/forge.db` directly (read-only) and shells out to `forge` for mutating actions.

## What this is

Under the v2 / RACI-driven model, forge sessions are mostly agent-driven — the orchestrator (Claude Code in your terminal) calls `forge invoke` repeatedly, occasionally `forge new feature` for implementation work. The dashboard is not where you take action; it's where you **read what the agents wrote** and watch live runs land.

Navigation tabs:

- **home** — the default landing view, combining live host plan-limit windows with **In flight**, the one activity surface on Home: agent tasks plus compact **Host verification**, **CI checks**, **CI waits**, and **Operator waits** rows while those waits are actually in progress (FG-694/FG-731/FG-734; see below).
- **activity** — chronological agent outputs across every project on the host, rendered as markdown cards (not raw JSON). The same **In flight** surface remains at the top; agent tasks are not rendered a second time. Persisted launch and CI evidence is available under the collapsed **Diagnostics** disclosure.
- **projects** — one summary per canonical repository. Standalone clones and linked worktrees are nested as checkout/branch context; click the project for all-checkout activity or a checkout row for an exact-path operational filter. The registry surfaces only checkouts that still exist on disk or are operationally actionable: a missing checkout stays visible only while it has in-flight work or a live session, and is labeled missing/unavailable. A missing, idle checkout with no live session is suppressed, and a project whose checkouts are all suppressed drops off the view entirely — but its aggregate counts, last activity, and full historical `projectDirs` scope are preserved untouched for historical queries.
- **usage** — host Claude/Codex plan-limit windows plus token usage rollup and time-series, grouped by role / workflow / project / model. Claude OAuth limits come from an observed Anthropic usage integration; it is not treated as a stable public API contract. Current Codex limits come from the documented local Codex App Server `account/rateLimits/read` method, not a public provider HTTPS endpoint. A bounded scan of recent local rollout files is retained only as a compatibility fallback, and fallback data is labeled stale with its observation time. Coexisting Claude, Anthropic API, Bedrock, Codex subscription, and OpenAI API channels render independently when configuration or an observation proves they exist. Bedrock and API-key channels use explicit non-subscription states rather than invented quota numbers.
- **ops** — operational metrics rollup, plus a runtime-trend panel with a metric selector (FG-683) between two deliberately distinct metrics: **Average agent runtime** (the default) observes agent *tasks* and reports their mean duration, while **Completed runs** observes *runs* and reports a plain count — switching the selector switches what is being measured, not just how it is drawn. **Average agent runtime** is a bar chart of the mean duration of completed agent tasks over a `1d` / `7d` / `30d` / `90d` / `all` window (hourly buckets on `1d`, daily on `7d`/`30d`, weekly on `90d`/`all`), charting "All agents" by default or a single observed role, with a role breakdown table (average + run count) whose rows re-chart the series. Buckets are keyed by completion time in UTC, and successful and failed agent *task attempts* both count — active work and the interactive orchestrator's own session task (`agent_role = 'orchestrator'` with `phase = 'session'`) do not. What each bar measures is the time the *agent* ran, not the time until its terminal was noticed (FG-662): where the run logged an attached container exit at or after its start, that exit ends the duration even if a later cancel, gate rejection or reconcile sweep rewrote the completion time; where it did not and the terminal was administrative — cancelled, gate-rejected, swept as orphaned, or swept into completion by reconcile or `forge recover --continue`, all of which stamp the completion time with the sweeping process's clock — the run has no defensible end and is left out of the chart altogether rather than plotted at the weeks-long span until someone noticed it. A run that is counted still sits in the bucket it *completed* in — only its duration comes off the agent's own exit. A bucket with no runs renders as a gap, never as a zero, and the bucket still in progress is hatched and captioned as one whose average can still move. Every number is readable off the chart surface itself (FG-648): a y-axis of gridlines ticked in duration units (`0s`, `24h`, `48h`, `72h`) whose top is rounded *up* to a whole step at or above the peak — an outlier is never clamped, truncated or log-compressed to make the rest of the series look tidier — plus each bucket's mean above its own bar and its sample count in the `RUNS` row beneath — despite the row's label, that count is agent *task attempts*, not completed forge runs; the **Completed runs** metric below is what counts runs. `0s` is the axis origin and nothing else: a sub-second mean reads `400ms` — on the bar, in the tooltip, and in the role and screen-reader tables alike — rather than rounding down into the one string this chart reserves for no duration at all. Every period the chart shows is rendered in a real timezone by `Intl.DateTimeFormat`, and the panel defaults to **Local** with a **Local / UTC** toggle beside the window buttons (FG-661). The bucket grid itself stays UTC-aligned — a local grid would put the same run in different buckets for different readers — so what the toggle changes is presentation, not data. Wherever there is room for it, a bucket is shown as its real range: `Jul 25 17:00 – Jul 26 17:00 PDT` in the bar's tooltip, the per-bucket list and the screen-reader table. That means a bar on the UTC grid legitimately opens at an odd local hour, and the chart says which one instead of handing the reader an offset to apply. Where the transition falls inside a bucket, its two ends carry the abbreviations they actually had — `Mar 7 16:00 PST – Mar 8 17:00 PDT` — which is the case a single stated offset could not express, and which is why the computed "You are UTC-7, so each UTC day here starts at…" caption was deleted rather than re-derived a third time. The x-axis, where a range does not fit, carries a compact form that still names its own zone in both modes (`7/25 PDT` in Local, `7/26 UTC` in UTC) — no date or clock time a reader can take off the plot is bare about which timezone it means. A label also has to name *one* bucket, so the compact form is kept only while it is unique within the window and the whole row escalates together when it is not: a `1d` window is 25 hourly buckets and therefore always spans two dates, which dates every hourly label (`8/1 14:00 PDT`), and an `all` window long enough to come round to a repeated week takes the year everywhere (`wk 3/4/19 UTC`). Switching the toggle re-renders every one of those surfaces together. Labels are thinned by measured width when they would collide, a bucket's mean and count are dropped when the mean would land on a neighbouring bar's fill rather than be drawn unreadably across it, and whenever any bucket loses either its period label or its mean and count, a wrapped per-bucket list beneath the plot carries all of them anyway — `Jul 25 17:00 – Jul 26 17:00 PDT 36m · 103 runs`, or `… no runs` for a gap. A screen-reader table repeats every bucket as text below the chart; the visible list is hidden from it, so those rows are announced once, not twice. A read that fails while the panel has no series to show — the first load, or a window switch that just dropped the previous one — is reported as an error and retried, never left as a permanent loading state. A read that starts failing *under* a series already on screen keeps that series and marks it stale beside the chart, so an operator who leaves the ops view open is never left reading frozen numbers as if they were current. **Completed runs**, the panel's other metric, counts forge runs, not tasks: exactly one observation per row of `runs` whose `status` is `complete`, whose `completed_at` is present and parseable, and whose `workflow` is not `orchestrator` — the interactive orchestrator's own instrumentation run is excluded at the run level, distinct from (though parallel to) the duration metric's task-level exclusion of the orchestrator's own session task above. Nothing is joined to the run, so a run's tasks, retries, fanout children, gates and host-verification rows cannot multiply its count, and placement is by `completed_at` regardless of when the run started. An empty bucket is a genuine `0`, not the missing-sample null the duration metric reports as a null average, and the panel also shows a running total summed across the plotted buckets, the current partial bucket included.
- **workbench** — read-only RACI Workbench. Four sections: SOURCE (active RACI file and kind), DERIVED (compiled routing-policy path and health), EFFECTIVE (routes in force and host→project diff, or null if the policy is broken), RECORDED (recent RACI audit log entries). Tab label is "workbench"; URL hash stays `#governance` for compatibility. No mutations — propose/apply is FG-361.
- **backlog** — read-only view of the selected project's backlog. Tickets are **host-wide truth keyed by `project_key`**, not branch-local files: every checkout of one repository — canonical, feature branch, linked worktree, clone — renders the same rows, so selecting a feature checkout never exposes its branch-local ticket files. A repository that has never been imported into the forge store has no ticket truth at all, and the board says so (with the `forge backlog import` repair) rather than rendering an empty board; a failed ticket read renders as an error, never as zero tickets. A project still in markdown mode shows its rows badged as a non-authoritative import shadow. Session handoff notes stay distinct operational context, retained per checkout. It is filterable by type and status and searchable by title and body, with a live count of matching results recalculated as those filters change. An exact checkout can still be selected. Mutations (create, close, move tickets) remain on the `forge backlog` CLI.
- **campaigns** (FG-395) — read-only list of recent campaigns (progress counts, current item, verdict) that opens onto one campaign's full report. Renders **exactly** the `forge campaign report` contract — no dashboard-SQL re-derivation of done-audit, readiness, verdict, next-action, or git state — so blocked/shipped/skipped/held/failed groupings, blocker reasons and requested actions, and per-item git/PR evidence (branch/worktree/commit; a null `prUrl` renders as no PR, never a fabricated link) match the CLI exactly. Works unscoped (every project's campaigns) or project-scoped. An unreadable store (e.g. one that predates the campaign tables) renders as "Campaigns unreadable" rather than an empty list; an unknown campaign id is a 404.
- **control-plane** (FG-349) — read-only EFFECTIVE config graph for one exact checkout: which config Forge would use for a run here, with provenance. Two panels: **Sources** (one row per config surface — project dir, forge home, workflow, runtime, model policy, routing policy/RACI, docs surfaces, constraints, installed agents, installed workflows, seed generation, seed drift — each carrying a `SOURCE | DERIVED | EFFECTIVE` truth axis, a `active | absent | overridden | template-only | derived | stale | missing | warning` status, and, where it applies, an override callout naming the full-replacement or merge semantics verbatim) and **Capabilities** (provider/auth readiness by env-var presence, the adapter capability matrix, and Shipping Reviewer / Campaign Runner prerequisite readiness — host-observed facts kept visually distinct from facts inferred about the would-be run container). Checkout-specific like workbench: a `projectKey` without an exact `projectDir` is refused (a project with more than one checkout has no single graph). Deep-linkable at `#control-plane`. Backed by the SAME `buildConfigGraph()` the `forge config graph [--json]` CLI prints, returned unmodified, so the two surfaces are byte-identical. No mutation.

Click any activity card to see the full result.json + container stdout + related verdicts/gates.

## In flight and current-activity diagnostics

**In flight** answers one question — *is something happening, or is this stuck?* Agent rows come from `/api/in-flight`; compact host-verification, CI-check, CI-wait, and operator-wait waits come from the durable FG-679/FG-731/FG-734 projection. An agent is never rendered from both.

The full persisted evidence lives under **Diagnostics** on the activity view and in `forge status`. It is not another visible activity summary and it does not render agent rows.

- **Host verification** — durable launches (`forge launch run`) that **declared `--purpose host_verification`** at submission, read from persisted observations. A launch is **never** rendered as an agent task, however long it runs.
- **Launch activity** — every other placed launch, under whatever purpose it declared (`agent_invoke`, `review`, `campaign`, `dashboard`, `generic`) plus every legacy row recorded before the field existed. Same full diagnostic row — status, identity, argv — under a heading that claims nothing about the launch beyond the purpose the row itself carries. It renders only when there is something in it, the way **Unassociated activity** does.
- **CI checks** — checks in progress for the current PR candidate. Forge's store calls these the required shipping checks; that protocol term is not exposed as the dashboard heading. The dashboard asks GitHub nothing.
- **CI waits** (FG-731) — durable, explicitly **registered** Forge-owned CI waits (`forge ci-wait`): required PR checks, a push-triggered Actions run, or a `workflow_dispatch` run registered *before* polling started. Unlike Host verification and CI checks, a non-terminal wait renders and forces non-idle by its mere **presence**, regardless of how stale its last observation is — a wait whose registering process died is recovered by re-observing `gh`, never silently dropped. States: `CI running m/n`, `no CI is running` (`no_runs` — distinct from unavailable), `CI state unavailable` (undetermined, or too stale to trust), and `CI completed — awaiting advance` (a `forge advance`/`forge continue` is still owed — never rendered as finished, never dropped). Each row shows one aggregate line, not a check-by-check history.
- **Operator waits** (FG-734) — every live `waiting_on_operator` entry, **derived** (no new table) from a task parked at a `human`-gated workflow step (`human_gate`) or a `campaign_items` row that recorded a `requested_human_action` (`campaign_hard_stop`); a human gate and a hard stop naming the same run de-duplicate to one entry. Like CI waits, a row's mere **presence** forces non-idle regardless of what else is in scope. Each row carries its source, an identity (the ticket, else the run id), the reason Forge stopped, and the requested action — never inferred from log text, an agent's own message, or elapsed time.

Before this existed, a run whose only in-flight work was host verification or a pending check read as though nothing was happening, because neither is a task row.

**What a launch IS comes from its declared purpose, never from its association (FG-700).** `forge launch run --purpose <host_verification|agent_invoke|review|campaign|dashboard|generic>` records it at submission; an unrecognized value is refused before anything is launched or recorded. Association (`--run` / `--task` / `--ticket`) answers *where* a launch belongs and is not consulted for the label, and nothing is ever read out of the launch's name, argv, command text or logs. A NULL, empty or unrecognized purpose fails closed to `generic`, so a row written before FG-700 is a generic launch and never host verification — nothing is backfilled or inferred from history. Until FG-700 the projection had no purpose to consult and used the presence of an association as a stand-in, which is how every associated `forge invoke`, review and campaign launch rendered as a host-verification wait, duplicating work the agent rows already showed.

**Launch statuses are projected exactly as `forge launch show` prints them.** These are four different facts, and none of them is a generic `failed`:

- `terminated by SIGTERM (signal sender not recorded — origin unknown)` — the kernel proved a signal landed; who sent it is recorded nowhere.
- `exited 143 (signal-range code, no signal evidence — origin unknown)` — a bare exit code in the signal range with **no** signal evidence. **Exit 143 alone is never attribution evidence**: a command may deliberately return 143, so it is reported as the code it is and never upgraded into a kill claim.
- `owner gone without an exit record (wrapper killed, or failed before recording — cause and sender not recorded)` — a live session holding a dead pane; durable evidence the wrapper never finished its last act, not that it was killed.
- `unknown (no exit record, owner gone — e.g. host reboot)` — no exit record and no live owner.

**A persisted observation is evidence of what was observed and when — never a claim about the present.** A stale or incomplete observation renders `unobserved since <time>`, never fabricated as `running` and never as terminal; the absence of a fresh observation is a fact about the observer, not about the work. A hand-run launch's freshness comes only from opportunistic promotion at the next `forge next` / `gate` / `continue` / `status` (there is no daemon), so a gap between them reads `unobserved since <time>`.

For required CI, the section itself is one of three states (FG-694): **`no current CI candidate`** (nothing in scope — no active run, no open review — could be waiting on required checks, so no CI row renders at all), **`CI not observed`** (current work IS in scope and no observation exists for it — nobody looked, which is not evidence CI is idle), or **`observed`**, where each observation carries its own state — **`CI not running`** (the newest observation resolved and enumerates no pending contexts) or **`stale`** (an observation exists but is past the freshness cutoff, labeled as such rather than shown as current). "Current" is read from the persisted `runs`/`reviews` rows (an active run, or a review whose state isn't terminal **and** whose ticket isn't closed — a `tickets.status` of `done` retires the review's observation the same way a terminal review state does, FG-694), never from an observation merely being newest for its run/project pair — see `docs/concepts.md` → **Current activity**. Each observation names the exact candidate sha and enumerates every required context with state, URL, and observation time; when the candidate moves, old-sha evidence disappears rather than being carried forward or relabeled.

### In flight waits (FG-694 post-ship correction)

Home and Activity fold a narrow set of **waits** into the existing **In flight** list — never a second visible activity panel, and never a second agent list:

- **Host verification** — a launch renders as a wait only when it **declared `--purpose host_verification`** at submission (FG-700), **and** it is **associated** with current work (it declared `--run`, `--task`, or `--ticket`), **and** its freshest observation says **running**. A launch that declared any other purpose or none, a stale observation, a terminal disposition (`exited …`, `terminated by …`, `owner gone`, `unknown`), or an unassociated launch (including a host-level launch nobody tied to a run, project, or task — e.g. the dashboard server itself) stays off Home entirely; all of it is still on the activity view and in `forge status`, unchanged.
- **CI checks** — a candidate renders only while its PR checks are genuinely pending. Passed, failed, not-started, stale, and unavailable observations are outcomes for Diagnostics/run/review detail, not in-progress rows.
- **CI waits** (FG-731) — every live, registered wait folds in **unconditionally**, unlike the two above: it is never filtered to a running-only or pending-only subset, because a registered wait is something the orchestrator is BLOCKED on. A stale or `completed_awaiting_advance` wait still renders on Home, carrying that honest label instead of a fabricated `running` or silently disappearing.
- **Operator waits** (FG-734) — every live `waiting_on_operator` entry folds in **unconditionally**, like CI waits: Forge has intentionally stopped and is owed a human decision, so a row's mere presence keeps Home `WAITING`, never `IDLE`, alongside whatever else is in flight.

Each wait is one line — an identity (the ticket, else the launch name, else its id; or the CI candidate label) and, for a host-verification or CI wait, elapsed time; a CI wait additionally shows its kind (`pr_checks` / `push_actions` / `workflow_dispatch`) and, while running, its `m/n` progress; an operator wait additionally shows its source (`human_gate` / `campaign_hard_stop`), the reason Forge stopped, and the requested action. No argv, no sha, no per-context breakdown — that detail is unchanged on the activity view. Nothing to wait on renders nothing at all, not an empty heading. A failed or malformed `/api/current-activity` read renders one line, `Host and CI waits unavailable`, with a retry affordance, distinct from a successful read that found nothing.

Read-only: no start, stop, or retry affordance for a launch or for CI (Home's retry is for the read itself, not for the underlying work), and launch detail is addressed by launch **identity** — no host filesystem path is accepted, exposed, or linked, and the log view is a bounded tail.

## HTTP API

The server exposes read-only JSON endpoints at `http://127.0.0.1:8024/api/…`. All `GET`. Notable surfaces:

- **`/api/feed`**, **`/api/in-flight`**, **`/api/projects`**, **`/api/task/:id`** — core activity data. Project records use a canonical repository `key`, aggregate counts, and retain `primaryCheckout`, exact `projectDirs`, and per-checkout path/branch/count records. The `/api/projects` per-checkout list is presentation-filtered to existing or operationally actionable checkouts (missing checkouts appear only with in-flight work or a live session); the aggregate counts, `lastRunAt`, and full historical `projectDirs` are never trimmed, so canonical `projectKey` scope still resolves every historical feed/usage/run record.
- **`/api/usage`**, **`/api/usage/timeseries`**, **`/api/usage/model-mix`** — token usage metrics
- **`/api/usage/limits`** — normalized host provider channels and plan windows; add `?refresh=1` to bypass the 30-second provider cache. Credentials and raw provider/App Server records remain server-side.
- **`/api/agent-runtime`** — average agent runtime over time, overall and per role, for the ops view's trend panel: TASK based (one observation per completed agent task). A duration derived from an exit event counts only when a `container.started` event for that attempt, recorded before that exit, proves a container was actually running when it stopped (FG-690) — host-side dependency resolution, provisioning refusals, and failed Docker starts are not agent execution and are excluded rather than charted as one. `?window=1d|7d|30d|90d|all` (default `7d`); an unrecognized window is a `400`, never a silent fallback. Empty buckets report `sampleCount: 0` with a null average rather than a zero duration.
- **`/api/completed-runs`** (FG-683) — the throughput sibling of `/api/agent-runtime`, for the same trend panel: RUN based (one observation per completed run, excluding the interactive orchestrator's own run), not task based. Same `?window=` values and default, same `400` on an unrecognized one. Empty buckets report `completedRuns: 0` — always a number, never null.
- **`/api/current-activity`** — the Current activity projection for a scope: `agents`, `hostVerification`, `launches` (FG-700's generic launch-diagnostics bucket, disjoint from `hostVerification` by declared purpose), `requiredCi`, `ciWaits` (FG-731), and `operatorWaits` (FG-734), plus the host-level `unassociated` bucket. Reads persisted rows only: task rows, `launch_observations`, the newest `review_loop.ci_observed` observation, the registered `ci_waits` table, and the durable `tasks`/`campaign_items` rows an operator wait derives from. Backed by the SAME exported derivation (`src/v2/current-activity.ts`) that `forge status` renders, so the two surfaces agree structurally rather than by convention.
- **`/api/launches/:id`**, **`/api/launches/:id/log`** — launch detail and a **bounded** log tail, addressed by launch identity. The id is validated against the launch-id charset before it is ever used as a path; `..`, absolute paths, and anything outside that charset are rejected `4xx`, and no response body or rendered link carries a host filesystem path.
- **`/api/campaigns`**, **`/api/campaign/:id`** (FG-395) — the campaigns tab's read path: cheap per-campaign summaries and one campaign's full `forge campaign report` result, reused rather than re-derived. `/api/campaigns` accepts `?projectKey=`/`?projectDir=` (unscoped lists every project) and `?limit=` (default 50, clamped `[1, 200]`). A store read that throws (unavailable/malformed store) is `503` on both routes, distinct from a legitimately empty list (`200`) and an unknown id (`404`).
- **`/api/config-graph`** (FG-349) — the control-plane tab's read path: `buildConfigGraph()` for one exact checkout (`?projectDir=`), the same object `forge config graph --json` prints, unmodified. `?projectKey=` alone (no exact `projectDir`) is a `409`, like `/api/governance` — a project with more than one checkout has no single graph. The payload is built before `writeHead` so a degraded read (a thrown build) returns `200 {error}` rather than a half-written response; on the success path every string in the graph is redacted (`redactSecrets`) as defense-in-depth over the per-row redaction the section builders already do, and on the degraded path the caught error's own message is routed through the same `redactSecrets` before it lands in `{error}`, so a secret surfaced via an exception string carries the same redaction guarantee as one that would have reached the graph object.
- **`/api/backlog`** — accepts canonical `?projectKey=<key>` or exact `?projectDir=<dir>`. Tickets come from the host store, scoped by the `project_key` the server derives from its **own** registry resolution of that request (the request's `projectKey` parameter is never used as a store key — trusting it would turn a per-project board into a cross-project one). Both request shapes therefore answer identically for one repository, and no branch-local ticket file is read. The response carries `ticketsProjectKey` (null when the repository has no ticket truth), `ticketsStorageMode` (`db` | `markdown` | null) and an optional `ticketsError` alongside `tickets`. Session handoff notes stay per-selection and per-checkout: a canonical response exposes every checkout's notes via `notesByCheckout`, and an exact single-checkout response also fills the legacy `notes` field. Read-only.

The FG-679 endpoints (`/api/current-activity`, `/api/launches/:id`, `/api/launches/:id/log`) make **no outbound call while serving or polling** — no GitHub, no shell, no `git`, no Forge CLI, no tmux — and never call `readLaunch` or `listLaunches`, whose status classification is a live tmux probe rather than a read of durable state. A runtime guard proves it, rather than inspection. Two pre-existing serving paths elsewhere in the server *do* shell out (FG-290's `docker inspect` on `/api/in-flight`, and project presentation's `git`); they are recorded as named exceptions in `docs/plans/fg679-current-activity-architecture.md`, and the guard is deliberately scoped to the new paths rather than widened over them.

Project-aware read endpoints accept either `?projectKey=<canonical-key>` to include every observed member path or `?projectDir=/exact/path` for an exact operational checkout. If both are present, the exact path wins. Unknown canonical keys match nothing. Metrics endpoints also accept `?since=30d` — except `/api/agent-runtime` and `/api/completed-runs`, which take a fixed `?window=` instead. Full parameter and response-shape reference: `docs/SCHEMA-CONTRACT.md`.

## Relationship to forge

This package reads forge's SQLite + filesystem layout but does not write to either. Mutating actions (gate decisions, run-next, retry) shell out to the `forge` CLI binary — it must be on `$PATH`. Install it the supported way: build a release, promote it, and install the shim once (`forge release build` / `promote` / `install-shim` — see the root README). Not `npm link`, which would put the live checkout on `$PATH` as `forge` and bypass the promoted release entirely.

Schema coupling is now enforced at the TypeScript level: `src/queries.ts` imports its row types from `@forge/types` (aliased to `../src/types/index.ts`). Any forge schema change that breaks the dashboard surfaces as a `npm --workspace=dashboard typecheck` failure.
