# Forge Invariants

A compact set of rules for reasoning about forge's control plane. Humans, orchestrators, and agents should be able to re-derive most decisions from these rather than from folklore. This is a compression layer, not a tutorial — see `docs/concepts.md` for the full glossary and the `how-to-*.md` files for procedure.

If a discussion needs a rule not listed here, that's a signal the rule should either get added here or doesn't actually hold system-wide.

## Vocabulary

- **SOURCE** — the human-authored or version-controlled origin of a rule or config. Something a person edits directly.
- **DERIVED** — mechanically produced from a SOURCE by a compiler/loader, never hand-edited as the primary path (an escape hatch may exist, but it's explicitly unsupported).
- **EFFECTIVE** — the value actually in force for one concrete dispatch or host, after precedence and overrides are resolved.
- **RECORDED** — a fact persisted at the moment something happened. Read back as history, never recomputed — it describes what was true *then*, not what is true now.

## The invariants

1. **SQLite (`~/.forge/forge.db`) is the SOURCE of run/task lifecycle truth.** Task artifacts (`result.json`, stderr, worktree diffs) are evidence for a task row's state, not the state itself.
2. **A run's status is one of `active | complete | failed | abandoned`.** `complete` and `failed` are both terminal outcomes of a settled run: `complete` means every declared phase settled successfully, `failed` means the run settled but a required phase failed OR a downstream phase became permanently unreachable (a `run.failed` lifecycle event is emitted); `abandoned` is operator cancel (FG-585). A run may still `complete` while containing a *superseded* failed task — a failed phase that itself gains a successful **same-phase** replacement (a request-changes re-run of that phase whose replacement completes) — but it can no longer `complete` while an *un-superseded* failed or unreachable required phase remains. Supersession is per-phase: an `on_reject` recovery that re-runs a *different* (earlier) phase does **not** supersede the failed phase — that phase keeps no complete primary of its own, so it stays failed/unreachable and the run settles to `failed`. Per-task detail still lives on individual task rows (`pending|running|awaiting_gate|awaiting_red|complete|failed|blocked_by_red|awaiting_recovery`).
3. **Project config fully replaces host config, file by file — it never merges.** If `<project>/.forge/` has its own `workflows/<name>.yml`, `model-policy.yml`, `routing-policy.yml`, or `docs-surfaces.yml`, that file is the EFFECTIVE one in its entirety; if it's absent, the host/built-in default applies whole.
4. **Host-installed config under `~/.forge/` is the EFFECTIVE runtime configuration.** Repo `seeds/` are SOURCE templates, copied in by `install-seeds.sh` / `forge upgrade`. For a **forge-owned** seed (runtimes, workflows, and the `forge-*` skills — the last installed into the user-global Claude Code skills dir rather than `~/.forge/`) editing the seed changes nothing until it's reinstalled, and `forge upgrade` (FORCE) reinstalls it. The **operator-authored** categories — `agents/`, `constraints/`, and `forge-raci.md` — are different: forge seeds them once (creating them when absent), after which the `~/.forge/` copy is the operator-owned SOURCE. No install re-writes an authored file — not under `FORCE=1`, not from any install path (FG-578) — so an edit to the repo seed does *not* propagate to a host that already has the file; the seed's authority over them is limited to first creation, and a divergent copy is reported (not refreshed), never overwritten. **For `constraints/` and `forge-raci.md` that is the whole rule, whole-file, unchanged.** For `agents/` it holds for everything *outside* one marker-fenced region per seed: the **Forge-owned agent protocol** — the review-protocol block a dispatched agent's output is judged against — is forge's, and `forge upgrade` publishes it deterministically into the operator's file while every line outside the fence survives byte-for-byte as the operator wrote it (FG-654). Position is preserved too, with one named exception the contiguity of the region forces: the fence takes the place of the sections it adopted, so the operator's `##` sections keep their order and their side of it, but a `###` of theirs nested *between* two Forge sections is re-emitted immediately after the closing fence rather than left inside the region — moved, never lost, and stated in `docs/how-to-upgrade.md` rather than discovered in a diff. The installer is unchanged and still writes no agent seed that already exists; upgrade is the single publisher of the region, and a legacy unmarked seed is adopted by that same pass — including one carrying only SOME of the region's headings, which is what every host seeded across the releases that grew the region actually holds, and which upgrade must adopt rather than refuse or that host is left unfenced and refused at every dispatch with no self-service remedy. Only a seed forge cannot read unambiguously at all is refused, with the repair named rather than guessed: a hand-edited fence, a DUPLICATED region heading, or a symlink standing where the seed belongs. Every published seed is committed by a single `rename(2)`, so an interrupted upgrade leaves no seed satisfying neither shape, and every path that discards bytes — adoption *and* re-publication over an existing fence — writes the named `.forge-pre-fg654.bak` first. The split exists because the two owners shared one overwrite-or-retain unit, so protecting the operator's half silently froze forge's: every discovery lens on an upgraded host kept running a pre-evidence-led review protocol nobody had told it had changed, which surfaced downstream as a malformed-output storm rather than as a seed problem. Identity is the *region's* content hash, never the file's, so an operator's own edits can never make a host read as stale — and a dispatch of a covered role whose region is stale, absent, or unfenced is refused **by name**, with `forge upgrade` as the remedy, rather than run under a contract nobody stated. The `seeds/` that get installed are always **the running forge's own**, resolved relative to the executing tree: a promoted release installs the release's bundled seeds, `forge-dev` installs your checkout's. Nothing ambient (`FORGE_REPO_DIR`, `--forge-repo`) redirects that — those name only the checkout that dev-advancement operates on (FG-577). For the **dispatch-coupled** forge-owned surface — workflows, runtimes, and the derived routing policy — the EFFECTIVE copy is not the flat `~/.forge/<category>` file but the **atomic seed generation** `forge upgrade` publishes: the complete set is committed by a single swap over a dedicated seed pointer, and every dispatch resolves that pointer once and reads one whole generation — never a torn or old/new-mixed set, and never the flat copies, which since FG-583 exist only for the drift detector and `forge doctor`'s registry. So editing or force-reinstalling a flat `~/.forge/workflows`/`runtimes` file changes nothing a `forge next` runs until `forge upgrade` republishes the generation; a torn/incomplete generation is a NAMED, repairable state (`forge doctor`), and dispatch refuses it rather than running under a set no release shipped.
5. **The RACI is SOURCE; `routing-policy.yml` is DERIVED; a resolved route is EFFECTIVE.** The human-authored `forge-raci.md` compiles to the typed policy — never the reverse — and `forge route explain` resolves the policy plus precedence into the one route a specific dispatch actually takes.
6. **Every task dispatch writes a RECORDED control-plane receipt** (workflow/runtime/model-policy/routing source + path, project mount mode, constraint counts, …). It is fixed at dispatch time and never recomputed — an Explain view reads history, not current config. Since FG-654 the same manifest carries a second dispatch-time receipt under the same discipline — the **agent protocol generation** the dispatch actually ran under (`agentProtocol`, a sibling block rather than a field inside `controlPlane`): the role plus the content hash of the Forge-owned region in the seed that was composed into its prompt — so "which protocol was this agent told" is read back from durable state rather than inferred, and a retry re-resolves and re-stamps rather than replaying the original stamp. The review ledger keeps its own per-dispatch copy beside each lens outcome, but as an INDEX of that receipt rather than a second source of truth: where the two disagree the drift is stated, not reconciled (invariant 20's discipline). A review whose stages span an upgrade legitimately mixes generations; the mix is recorded per dispatch, not prevented.
7. **Model policy decides who runs a task; workflow YAML decides what work happens.** Provider, auth, and concrete model resolve from model policy by capability; steps, gates, reds, and fanout shape come from the workflow definition. The two resolve independently.
8. **Runtime YAML describes how a provider/model is actually executed** — image, mounts, invocation args, auth strategy — one layer beneath model policy, which only chooses which runtime applies.
9. **Red agents are always mounted read-only on the project at the OS/container level.** This is Docker mount enforcement (`:ro`), never a prompt instruction, and it is never relaxed for any red. It is a **write** guarantee, not a confidentiality one: when the project is a linked git worktree, the parent repo's `.git` is bound read-only as well (FG-559), so a red can read the full repository history — every branch, tag, remote-tracking ref, the reflog — while every write is still refused by the kernel. What reds must not receive is other panel members' findings and the blue's transcript, and those never live in `.git`. (See `docs/concepts.md` → Red agent, Worktree git access.)
10. **All state mutation goes through the forge control plane.** The dashboard reads `~/.forge/forge.db` directly but mutates nothing itself — any dashboard action that changes state shells out to the `forge` CLI, keeping one enforcement path for auth and validation.
11. **Agents are fallible workers, not the trust boundary.** Gates, red review, host verification/tests, and CI are the trust boundary — a task or agent claiming success is not itself sufficient evidence that it's true.
12. **Durable docs are maintained deliberately, not as a side effect.** A dedicated pass (the documentation-maintainer, or an explicit docs-impact resolution) reconciles docs against ground truth; nobody edits `docs/**` or `README*` casually mid-conversation.
13. **The publish target never holds UNVALIDATED work — it fast-forwards to a fully-validated commit, or it does not move.** Validation (tests, integration gate, reds, review) runs against a candidate commit built in a throwaway integration worktree, never against the target; the exact validated SHA is then published through a short compare-and-swap window. A failed gate, a refused CAS, or a dirty target leaves the target unchanged — so there is never a bad merge on the target to undo. **But a validated candidate that has already WON the CAS is durably published.** A crash after the ref advance leaves a publication that recovery **completes** (finishing the outstanding working-tree checkout) rather than undoes — recovery decides from `{baseSha, candidateSha, currentTargetSha}` and the RECORDED target ref, never from working-tree contents (AD-5). So "crash mid-publish" does not mean "nothing was published": it means *ask recovery*, and never hand-roll a rollback. (FG-425; `learnings/decisions/serialized-integration-publisher.md`.)
14. **A publisher that has lost the publication window mutates NOTHING, and no terminal claim may stand over an unsettled publication.** Once a publisher discovers it no longer owns the short mutex, it executes no target-mutating command — not `update-ref`, `read-tree`, `checkout`, `reset`, or cleanup, and not even a rollback of its own ref advance (the window's new owner may already have synchronized the tree onto the candidate, so a compare-and-swap "undo" would still corrupt the target). It preserves the durable publishing intent instead, and only AD-5 convergence — never a lane sweep — may settle an attempt recorded `publishing`. A task whose publication is unsettled parks in the non-terminal `awaiting_recovery`; a terminal refusal claiming "nothing was published" may never stand over an attempt whose ref advance landed, because it invites a retry of work that is already on the target. (FG-425 AC5; FORGE-DEC-027, `learnings/decisions/2026-07-13_awaiting-recovery-task-status.md`.)
15. **Accountability for what ships is always human.** Automation can gate, verify, and recommend, but responsibility for what merges or ships is never delegated to an agent or a passing check alone.
16. **Exactly one store is the SOURCE of a project's backlog tickets, and which one is held host-side under `project_key`.** A project's storage mode is `markdown` (files under `backlog/`, the default) or `db` (rows in `~/.forge/forge.db`) — never both. It lives in the DB keyed by `project_key`, never in a worktree's git-tracked `.forge/config.yml`, so two linked worktrees of one project cannot disagree about which store owns the tickets. Reads and writes go to the authoritative store alone: **no read-through blending of the two, and no silent fallback from one to the other** — a ticket absent from the authoritative store does not exist, and a failed db-mode write is never rescued by a file on disk. Because the store is keyed by `project_key` and not by a checkout, **ticket truth is host-wide, never branch-local**: every checkout of one repository — canonical, feature branch, linked worktree, clone — answers with the same rows, and the dashboard derives that key from its own project resolution rather than from a request parameter. Changing the mode is an explicit operator act (`forge backlog mode --set`, or the atomic cutover `forge backlog migrate`) that refuses rather than strand tickets in an unread store — and the cutover to `db` is **one-way in practice, enforced**: there is no Markdown export, so a migrated project's `backlog/*.md` freezes, the first DB-only edit is RECORDED, and reverting to `markdown` afterwards refuses rather than silently discarding every edit since. (FG-607, FG-608; see `docs/concepts.md` → Backlog storage mode and `docs/how-to-backlog-db-cutover.md`.)
17. **A task workspace is disposed of only against proof its work was captured; anything unproven is RETAINED with a recorded reason.** Forge removes a task workspace and its branch on exactly three warrants: a failed *setup* before any agent ran (there is no output yet), the explicit ephemeral/test opt-in (`FORGE_WORKTREES_EPHEMERAL=1`), or **proof of capture** — one of the two substrates forge creates, proved to be *this task's*, a clean tree including git-ignored files, and every branch/`HEAD` commit reachable from Forge-owned state (`run.projectDir`'s `HEAD`, or a SHA the publisher recorded as published — `HEAD` alone is a proxy a `remote:` target never advances). That bar holds on the dispatch path (`removeWorktreeIfSafe`, only after a proven publication) and, since FG-356, in reconcile's state-keyed sweep of terminal tasks — the only thing that ever reclaims a workspace whose own cleanup died with its forge process. Where reaping and retaining disagree — an unreadable git probe, an unrecognized substrate, a failure kind whose workspace IS the evidence (`merge_conflict`, `capture_failed`, the integration/publication kinds) — the retain wins, and a durable `task.workspace_retained` event names the path, the branch and the reason. So "the workspace is gone" always means "its work is captured", never "the work was discarded". **The retain-reason vocabulary is a published contract and only ever grows**: FG-621 added `remote_target_uncaptured` and stopped producing `private_clone_substrate` (the placeholder for the substrate whose disposal it implemented), but did not remove it — historical events carry it, and a reader must keep rendering every value it has ever emitted. A postponed decision is a third outcome, never a disguised one: while the parent repository is genuinely mid-`gc` a private clone's disposal is DEFERRED — neither reaped nor retained — and a deferral that persists is recorded as `task.workspace_reap_deferred` so it cannot become a silent, permanent limbo. (FG-356, FG-621; see `docs/concepts.md` → Reaping an orphaned workspace.)

18. **A mutating agent's write authority ends at its own repository; publication authority is Forge's alone.** Under workspace isolation a mutating agent gets a private `git clone --shared` at the task's recorded base SHA, on a deterministic private branch, with the parent's object store mounted **read-only** — so the parent's refs, index, object store and target branch are unwritable from inside any container as a property of the *mount*, not of a rule git is asked to enforce. The agent may commit freely there; those commits are untrusted checkpoints and transport artifacts. Only Forge builds the candidate, runs the authoritative gates and moves the target ref, and it may squash or replace the agent's commit boundaries. Capture is a fixed ordering — safety-commit the clone's remaining tracked **and untracked** state, resolve its branch tip, fetch that branch into the parent's ref namespace under the deterministic name, verify the fetched ref equals the tip, and only then publish — a failure at any step of that ordering is `capture_failed`, never a merge kind, because nothing has been merged — with **no clone-side commit after the fetch**, enforced by handing the publisher a source it was never told the workspace path of. A clone and its parent are different repositories, so a commit that landed after the fetch would be silently absent from the tree that was gated and published. (FG-621, FG-345, FG-340; see `docs/concepts.md` → Private writable Git for mutating agents.)

19. **A task workspace is committed content at the recorded base SHA plus what Forge explicitly supplies — ambient checkout state is never inherited.** Workspace isolation is the DEFAULT (FG-345, 2026-07-28), resolved as: `FORGE_NO_WORKTREES=1` off (highest precedence, outranking an explicit `FORGE_WORKTREES=1`), else an explicitly-set `FORGE_WORKTREES` honored, else the platform default — on for darwin, off elsewhere, because the preflight platform gate hard-fails on Linux and is permanent by design (the orchestrator is macOS-only; "Linux" in these gates means the agent container). What a workspace contains is exactly two things: the committed tracked content at the recorded base SHA, and inputs supplied through Forge's own provisioning or environment mechanisms (the dependency cache, the runtime's declared mounts and env, the task package). **Uncommitted, untracked and ignored files in the operator's checkout do not reach it, and that is the contract rather than a gap in it** — a workflow needing a local file supplies it through a Forge mechanism, and `FORGE_NO_WORKTREES=1` is the supported escape for anything the contract does not fit. The preflight gates are unchanged by default-on, but more dispatches now meet them: a non-git project and a dirty tracked tree both hard-fail, the latter bypassable only with `FORGE_WORKTREE_IGNORE_DIRTY=1`. **Scope: this is workflow dispatch** (`forge new` / `forge next`, primary and fan-out). `forge invoke` provisions no workspace and mounts the project directory itself, and `forge review-loop`'s red reviewer and fixer both dispatch through it — so those agents run on the shared checkout even where the default resolves on. (FG-345; see `docs/concepts.md` → Workspace isolation.)

20. **An agent container's ticket authority is ASSERTED BY THE MOUNT, and a container never reaches the host store.** What a container may read about tickets is decided by an unforgeable marker the host writes into a read-only directory mount before the container starts — never derived from the mounted checkout, the project registry, repository evidence, `.forge/config.yml`, or an environment variable the agent itself owns. What is mounted is a **derived, project-scoped, backlog-only snapshot database** holding one `project_key`'s tickets, relations and blocker evidence and no control-plane tables at all; the full `~/.forge/forge.db` is never mounted, so project isolation is structural rather than a filter. A container with no marker, a marker naming an authority it has no snapshot for, or a snapshot published for a different `project_key` **refuses to read** — it never falls back to `$HOME/.forge`, which inside a container is a shared named volume belonging to no project and would answer plausibly from another project's store. Reads are LIVE (the host republishes on every authoritative ticket write, so a post-start amendment reaches a running container), and every write refuses: the `:ro` bind is the enforcement, since agents have root in their own container, and the CLI's refusal is the polite half. Dispatch-time evidence (revision + body hash) and live authority are two RECORDED facts; neither overwrites the other, and a drift between them is stated rather than reconciled. (FG-608; see `docs/concepts.md` → Container ticket authority, `learnings/decisions/2026-07-29_container-backlog-snapshot-authority.md`.)

## Non-goals

This document does not replace `docs/concepts.md`, ADRs under `learnings/decisions/`, or the how-tos. It states the small set of rules that make the rest of those legible — not every mechanism, edge case, or recovery path.
