# Forge Invariants

A compact set of rules for reasoning about forge's control plane. Humans, orchestrators, and agents should be able to re-derive most decisions from these rather than from folklore. This is a compression layer, not a tutorial — see `docs/concepts.md` for the full glossary and the `how-to-*.md` files for procedure.

If a discussion needs a rule not listed here, that's a signal the rule should either get added here or doesn't actually hold system-wide.

## Vocabulary

- **SOURCE** — the human-authored or version-controlled origin of a rule or config. Something a person edits directly.
- **DERIVED** — mechanically produced from a SOURCE by a compiler/loader, never hand-edited as the primary path (an escape hatch may exist, but it's explicitly unsupported).
- **EFFECTIVE** — the value actually in force for one concrete dispatch or host, after precedence and overrides are resolved.
- **RECORDED** — a fact persisted at the moment something happened. Read back as history, never recomputed — it describes what was true *then*, not what is true now.

## The invariants

1. **SQLite (`~/.forge/forge.db`) is the SOURCE of run/task lifecycle truth.** Task artifacts (`result.json`, stderr, worktree diffs) are evidence for a task row's state, not the state itself.
2. **A run's status is one of `active | complete | failed | abandoned`.** `complete` and `failed` are both terminal outcomes of a settled run: `complete` means every declared phase settled successfully, `failed` means the run settled but a required phase failed OR a downstream phase became permanently unreachable (a `run.failed` lifecycle event is emitted); `abandoned` is operator cancel (FG-585). A run may still `complete` while containing a *superseded* failed task — a failed phase that itself gains a successful **same-phase** replacement (a request-changes re-run of that phase whose replacement completes) — but it can no longer `complete` while an *un-superseded* failed or unreachable required phase remains. Supersession is per-phase: an `on_reject` recovery that re-runs a *different* (earlier) phase does **not** supersede the failed phase — that phase keeps no complete primary of its own, so it stays failed/unreachable and the run settles to `failed`. Per-task detail still lives on individual task rows (`pending|running|awaiting_gate|awaiting_red|complete|failed|blocked_by_red|awaiting_recovery`).
3. **Project config fully replaces host config, file by file — it never merges.** If `<project>/.forge/` has its own `workflows/<name>.yml`, `model-policy.yml`, `routing-policy.yml`, or `docs-surfaces.yml`, that file is the EFFECTIVE one in its entirety; if it's absent, the host/built-in default applies whole.
4. **Host-installed config under `~/.forge/` is the EFFECTIVE runtime configuration.** Repo `seeds/` are SOURCE templates, copied in by `install-seeds.sh` / `forge upgrade`. For a **forge-owned** seed (runtimes, workflows, and the host/orchestrator skills — the last installed into the user-global Claude Code skills dir rather than `~/.forge/`) editing the seed changes nothing until it's reinstalled, and `forge upgrade` (FORCE) reinstalls it. The **operator-authored** categories — `agents/`, `constraints/`, and `forge-raci.md` — are different: forge seeds them once (creating them when absent), after which the `~/.forge/` copy is the operator-owned SOURCE. No install re-writes an authored file — not under `FORCE=1`, not from any install path (FG-578) — so an edit to the repo seed does *not* propagate to a host that already has the file; the seed's authority over them is limited to first creation, and a divergent copy is reported (not refreshed), never overwritten. **That is the whole rule for all three, whole-file, unchanged** — `agents/` included. Forge NEVER writes an operator-owned `~/.forge/agents/<role>/CLAUDE.md`: not a region inside it, not a splice, not a backup beside it. The **Forge-owned agent protocol** — the review-protocol block a dispatched agent's output is judged against — is forge's, and it does not live in the operator's file at all: it is `seeds/agent-protocols/<role>.md`, a forge-owned category of the same atomic seed generation that publishes workflows and runtimes, and compose puts it AHEAD of the operator's seed in the prompt (FG-654). The split exists because the two owners used to share one overwrite-or-retain unit, so protecting the operator's half silently froze forge's: every discovery lens on an upgraded host kept running a pre-evidence-led review protocol nobody had told it had changed, which surfaced downstream as a malformed-output storm rather than as a seed problem. Identity is the WHOLE protocol file's content hash, checked against the generation's own provenance manifest — an operator's own edits are in a different file entirely, so they can never make a host read as stale. A dispatch of a covered role whose protocol is absent from the generation, TORN (bytes that do not match that manifest), or STALE (manifest-consistent, but not the executing release's bytes — the state of a host that took a newer forge without `forge upgrade`) is refused **by name** before any container, mount or task dir exists, with `forge upgrade` as the remedy, rather than run under a contract nobody stated. The refusal is not silent, though: every dispatch path writes a durable **failed task row** carrying the refusal text — created already-failed on the workflow-red path, failed immediately after insert on the primary, fanout-child and `forge invoke` paths — so the refusal is addressable by task id and the review ledger can bind it to the lens that never ran. Two refusals name a repair forge will not perform for you: an installed seed still carrying an EMBEDDED legacy copy of the protocol — a marker-fenced leftover, or a heading this release's protocol owns — is refused until you delete that section by hand, because rewriting an operator-authored file is the thing this invariant forbids; and a release carrying no protocol for a covered role cannot publish a generation at all — nor dispatch one, because publication refuses only the generation it would have *created*, while a host already holding one published by an earlier, complete release has no baseline left to measure that generation's currency against and is refused at dispatch (and by `forge doctor`) too, with reinstalling the release rather than another upgrade as the remedy — so "published and healthy" can never mean "and one role refuses at every dispatch". The `seeds/` that get installed are always **the running forge's own**, resolved relative to the executing tree: a promoted release installs the release's bundled seeds, `forge-dev` installs your checkout's. Nothing ambient (`FORGE_REPO_DIR`, `--forge-repo`) redirects that — those name only the checkout that dev-advancement operates on (FG-577). For the **dispatch-coupled** forge-owned surface — workflows, runtimes, the agent protocols, and the derived routing policy — the EFFECTIVE copy is not the flat `~/.forge/<category>` file but the **atomic seed generation** `forge upgrade` publishes: the complete set is committed by a single swap over a dedicated seed pointer, and every dispatch resolves that pointer once and reads one whole generation — never a torn or old/new-mixed set, and never the flat copies, which since FG-583 exist only for the drift detector and `forge doctor`'s registry. So editing or force-reinstalling a flat `~/.forge/workflows`/`runtimes` file changes nothing a `forge next` runs until `forge upgrade` republishes the generation; a torn/incomplete generation is a NAMED, repairable state (`forge doctor`), and dispatch refuses it rather than running under a set no release shipped. The protocols have no flat copy at all — `install-seeds.sh` writes none — so `forge upgrade` is the only thing that moves them, and a host that ran the installer alone keeps dispatching under the generation it already had until it does.
5. **The RACI is SOURCE; `routing-policy.yml` is DERIVED; a resolved route is EFFECTIVE.** The human-authored `forge-raci.md` compiles to the typed policy — never the reverse — and `forge route explain` resolves the policy plus precedence into the one route a specific dispatch actually takes.
6. **Every task dispatch writes a RECORDED control-plane receipt** (workflow/runtime/model-policy/routing source + path, project mount mode, constraint counts, …). It is fixed at dispatch time and never recomputed — an Explain view reads history, not current config. Since FG-654 the same manifest carries a second dispatch-time receipt under the same discipline — the **agent protocol generation** the dispatch actually ran under (`agentProtocol`, a sibling block rather than a field inside `controlPlane`): the role, the sha256 of the WHOLE Forge-owned protocol file whose bytes were composed into its prompt, and that file's path inside the resolved seed generation — so "which protocol was this agent told" is read back from durable state rather than inferred, and a retry re-resolves and re-stamps rather than replaying the original stamp. The review ledger keeps its own per-dispatch copy beside each lens outcome, but as an INDEX of that receipt rather than a second source of truth: where the two disagree the drift is stated, not reconciled (invariant 20's discipline). A review whose stages span an upgrade legitimately mixes generations; the mix is recorded per dispatch, not prevented.
7. **Model policy decides who runs a task; workflow YAML decides what work happens.** Provider, auth, and concrete model resolve from model policy by capability; steps, gates, reds, and fanout shape come from the workflow definition. The two resolve independently.
8. **Runtime YAML describes how a provider/model is actually executed** — image, mounts, invocation args, auth strategy — one layer beneath model policy, which only chooses which runtime applies.
9. **Red agents are always mounted read-only on the project at the OS/container level.** This is Docker mount enforcement (`:ro`), never a prompt instruction, and it is never relaxed for any red. It is a **write** guarantee, not a confidentiality one: when the project is a linked git worktree, the parent repo's `.git` is bound read-only as well (FG-559), so a red can read the full repository history — every branch, tag, remote-tracking ref, the reflog — while every write is still refused by the kernel. What reds must not receive is other panel members' findings and the blue's transcript, and those never live in `.git`. (See `docs/concepts.md` → Red agent, Worktree git access.)
10. **All state mutation goes through the forge control plane.** The dashboard reads `~/.forge/forge.db` directly but mutates nothing itself — any dashboard action that changes state shells out to the `forge` CLI, keeping one enforcement path for auth and validation.
11. **Agents are fallible workers, not the trust boundary.** Gates, red review, host verification/tests, and CI are the trust boundary — a task or agent claiming success is not itself sufficient evidence that it's true.
12. **Durable docs are maintained deliberately, not as a side effect.** A dedicated pass (the documentation-maintainer, or an explicit docs-impact resolution) reconciles docs against ground truth; nobody edits `docs/**` or `README*` casually mid-conversation.
13. **The publish target never holds UNVALIDATED work — it fast-forwards to a fully-validated commit, or it does not move.** Validation (tests, integration gate, reds, review) runs against a candidate commit built in a throwaway integration worktree, never against the target; the exact validated SHA is then published through a short compare-and-swap window. A failed gate, a refused CAS, or a dirty target leaves the target unchanged — so there is never a bad merge on the target to undo. **But a validated candidate that has already WON the CAS is durably published.** A crash after the ref advance leaves a publication that recovery **completes** (finishing the outstanding working-tree checkout) rather than undoes — recovery decides from `{baseSha, candidateSha, currentTargetSha}` and the RECORDED target ref, never from working-tree contents (AD-5). So "crash mid-publish" does not mean "nothing was published": it means *ask recovery*, and never hand-roll a rollback. (FG-425; `learnings/decisions/serialized-integration-publisher.md`.)
14. **A publisher that has lost the publication window mutates NOTHING, and no terminal claim may stand over an unsettled publication.** Once a publisher discovers it no longer owns the short mutex, it executes no target-mutating command — not `update-ref`, `read-tree`, `checkout`, `reset`, or cleanup, and not even a rollback of its own ref advance (the window's new owner may already have synchronized the tree onto the candidate, so a compare-and-swap "undo" would still corrupt the target). It preserves the durable publishing intent instead, and only AD-5 convergence — never a lane sweep — may settle an attempt recorded `publishing`. A task whose publication is unsettled parks in the non-terminal `awaiting_recovery`; a terminal refusal claiming "nothing was published" may never stand over an attempt whose ref advance landed, because it invites a retry of work that is already on the target. **The converse is the same rule, and it bounds what reconciliation may touch: a terminal state a human CHOSE is never reconciled away by a background sweep.** Reconciliation may correct a terminal claim that was *inflicted* — a crash, a lost window, a database predating this rule — never one that was *decided*. The publication record is authoritative for whether a candidate reached the target; the task row is authoritative for what disposition a human chose, so a `forge cancel`, a gate `reject` and a gate `request-changes` stand over a `published` attempt, keep their error and rejection rationale, and remain immutable audit history. Where nothing on the timeline records a human's decision the default is unchanged and still reconciles, which is what keeps the crash-stranded case working. A row a pre-FG-676 sweep already resurrected does not clear on a later wave — it is operator-repairable (`forge ops check` → `forge ops repair`), never self-healed. (FG-425 AC5, FG-676; FORGE-DEC-027, `learnings/decisions/2026-07-13_awaiting-recovery-task-status.md`.)
15. **Accountability for what ships is always human.** Automation can gate, verify, and recommend, but responsibility for what merges or ships is never delegated to an agent or a passing check alone.
16. **Exactly one store is the SOURCE of a project's backlog tickets, and which one is held host-side under `project_key`.** A project's storage mode is `markdown` (files under `backlog/`, the default) or `db` (rows in `~/.forge/forge.db`) — never both. It lives in the DB keyed by `project_key`, never in a worktree's git-tracked `.forge/config.yml`, so two linked worktrees of one project cannot disagree about which store owns the tickets. Reads and writes go to the authoritative store alone: **no read-through blending of the two, and no silent fallback from one to the other** — a ticket absent from the authoritative store does not exist, and a failed db-mode write is never rescued by a file on disk. Because the store is keyed by `project_key` and not by a checkout, **ticket truth is host-wide, never branch-local**: every checkout of one repository — canonical, feature branch, linked worktree, clone — answers with the same rows, and the dashboard derives that key from its own project resolution rather than from a request parameter. Changing the mode is an explicit operator act (`forge backlog mode --set`, or the atomic cutover `forge backlog migrate`) that refuses rather than strand tickets in an unread store — and the cutover to `db` is **one-way in practice, enforced**: there is no Markdown export, so a migrated project's `backlog/*.md` freezes, the first DB-only edit is RECORDED, and reverting to `markdown` afterwards refuses rather than silently discarding every edit since. (FG-607, FG-608; see `docs/concepts.md` → Backlog storage mode and `docs/how-to-backlog-db-cutover.md`.)
17. **A task workspace is disposed of only against proof its work was captured; anything unproven is RETAINED with a recorded reason.** Forge removes a task workspace and its branch on exactly three warrants: a failed *setup* before any agent ran (there is no output yet), the explicit ephemeral/test opt-in (`FORGE_WORKTREES_EPHEMERAL=1`), or **proof of capture** — one of the two substrates forge creates, proved to be *this task's*, a clean tree including git-ignored files, and every branch/`HEAD` commit reachable from Forge-owned state (`run.projectDir`'s `HEAD`, or a SHA the publisher recorded as published — `HEAD` alone is a proxy a `remote:` target never advances). That bar holds on the dispatch path (`removeWorktreeIfSafe`, only after a proven publication) and, since FG-356, in reconcile's state-keyed sweep of terminal tasks — the only thing that ever reclaims a workspace whose own cleanup died with its forge process. Where reaping and retaining disagree — an unreadable git probe, an unrecognized substrate, a failure kind whose workspace IS the evidence (`merge_conflict`, `capture_failed`, the integration/publication kinds) — the retain wins, and a durable `task.workspace_retained` event names the path, the branch and the reason. So "the workspace is gone" always means "its work is captured", never "the work was discarded". **The retain-reason vocabulary is a published contract and only ever grows**: FG-621 added `remote_target_uncaptured` and stopped producing `private_clone_substrate` (the placeholder for the substrate whose disposal it implemented), but did not remove it — historical events carry it, and a reader must keep rendering every value it has ever emitted. A postponed decision is a third outcome, never a disguised one: while the parent repository is genuinely mid-`gc` a private clone's disposal is DEFERRED — neither reaped nor retained — and a deferral that persists is recorded as `task.workspace_reap_deferred` so it cannot become a silent, permanent limbo. (FG-356, FG-621; see `docs/concepts.md` → Reaping an orphaned workspace.)

18. **A mutating agent's write authority ends at its own repository; publication authority is Forge's alone.** Under workspace isolation a mutating agent gets a private `git clone --shared` at the task's recorded base SHA, on a deterministic private branch, with the parent's object store mounted **read-only** — so the parent's refs, index, object store and target branch are unwritable from inside any container as a property of the *mount*, not of a rule git is asked to enforce. The agent may commit freely there; those commits are untrusted checkpoints and transport artifacts. Only Forge builds the candidate, runs the authoritative gates and moves the target ref, and it may squash or replace the agent's commit boundaries. Capture is a fixed ordering — safety-commit the clone's remaining tracked **and untracked** state, resolve its branch tip, fetch that branch into the parent's ref namespace under the deterministic name, verify the fetched ref equals the tip, and only then publish — a failure at any step of that ordering is `capture_failed`, never a merge kind, because nothing has been merged — with **no clone-side commit after the fetch**, enforced by handing the publisher a source it was never told the workspace path of. A clone and its parent are different repositories, so a commit that landed after the fetch would be silently absent from the tree that was gated and published. (FG-621, FG-345, FG-340; see `docs/concepts.md` → Private writable Git for mutating agents.)

19. **A task workspace is committed content at the recorded base SHA plus what Forge explicitly supplies — ambient checkout state is never inherited.** Workspace isolation is the DEFAULT (FG-345, 2026-07-28), resolved as: `FORGE_NO_WORKTREES=1` off (highest precedence, outranking an explicit `FORGE_WORKTREES=1`), else an explicitly-set `FORGE_WORKTREES` honored, else the platform default — on for darwin, off elsewhere, because the preflight platform gate hard-fails on Linux and is permanent by design (the orchestrator is macOS-only; "Linux" in these gates means the agent container). What a workspace contains is exactly two things: the committed tracked content at the recorded base SHA, and inputs supplied through Forge's own provisioning or environment mechanisms (the dependency cache, the runtime's declared mounts and env, the task package). **Uncommitted, untracked and ignored files in the operator's checkout do not reach it, and that is the contract rather than a gap in it** — a workflow needing a local file supplies it through a Forge mechanism, and `FORGE_NO_WORKTREES=1` is the supported escape for anything the contract does not fit. The preflight gates are unchanged by default-on, but more dispatches now meet them: a non-git project and a dirty tracked tree both hard-fail, the latter bypassable only with `FORGE_WORKTREE_IGNORE_DIRTY=1`. **Scope: this is workflow dispatch** (`forge new` / `forge next`, primary and fan-out). `forge invoke` provisions no workspace and mounts the project directory itself, and `forge review-loop`'s red reviewer and fixer both dispatch through it — so those agents run on the shared checkout even where the default resolves on. **Every eligible dispatch that mounts a project resolves its dependency environment host-side before any agent container starts, read-only and read-write alike, through ONE resolver** — `forge invoke`'s reviewers and reds, `forge invoke`'s writable lane, and a workflow's own pipeline reds and read-write primaries — and is refused pre-container (`verification_environment_unavailable`) rather than started into a workspace whose declared dependencies it cannot load: recorded by the review lane as `blocked_environment`, and parking a workflow step `blocked_by_red`. `forge invoke`'s writable lane is **no longer the exception** it was between FG-664 and FG-678: an anonymous, empty `node_modules` shadow that masked whatever the operator had installed left "can this agent execute anything?" to be decided inside the container, so two interchangeable dispatches got different worlds and a validation task could report honestly that it was structurally unable to run — while its row still read `complete`. The environment is established by the platform, never improvised by the agent, and is **immutable for the dispatch**: the lockfile-keyed volumes are mounted `:ro` in every shape, so there is no shared writable cache over a live shared project directory (FG-376's race) and no container-side install can reach the operator's own tree. Resolution has three outcomes, not two — a project declaring no dependencies is *not applicable* and dispatches normally, a project declaring dependencies with a supported lockfile resolves, and a project declaring dependencies with no supported lockfile is unkeyable and refuses by name (`lockfile_absent`) rather than degrading into a workspace nobody attested (FG-664, FG-678; `learnings/decisions/2026-08-02_reviewer-dependency-environment.md`). (FG-345; see `docs/concepts.md` → Workspace isolation.)

20. **An agent container's ticket authority is ASSERTED BY THE MOUNT, and a container never reaches the host store.** What a container may read about tickets is decided by an unforgeable marker the host writes into a read-only directory mount before the container starts — never derived from the mounted checkout, the project registry, repository evidence, `.forge/config.yml`, or an environment variable the agent itself owns. What is mounted is a **derived, project-scoped, backlog-only snapshot database** holding one `project_key`'s tickets, relations and blocker evidence and no control-plane tables at all; the full `~/.forge/forge.db` is never mounted, so project isolation is structural rather than a filter. A container with no marker, a marker naming an authority it has no snapshot for, or a snapshot published for a different `project_key` **refuses to read** — it never falls back to `$HOME/.forge`, which inside a container is a shared named volume belonging to no project and would answer plausibly from another project's store. Reads are LIVE (the host republishes on every authoritative ticket write, so a post-start amendment reaches a running container), and every write refuses: the `:ro` bind is the enforcement, since agents have root in their own container, and the CLI's refusal is the polite half. Dispatch-time evidence (revision + body hash) and live authority are two RECORDED facts; neither overwrites the other, and a drift between them is stated rather than reconciled — a live snapshot that has moved past the dispatched revision says ADVANCED, and nothing claims the later revision is the one the task was built from. The identity that authority is RESOLVED AGAINST is Forge-owned durable run state — the run's recorded project directory — never the workspace that happens to host the task: a per-task clone is a disposable materialization of one run's tree at a recorded base SHA, so it answers mount questions, and asking it which project it owns is a category error. The substrates differ in a way nothing declared: a **linked worktree CONVERGES** with its parent's repository evidence (both resolve through the same git common dir), while a **private `git clone --shared` DIVERGES** — it gets its own common dir, and its filesystem-path `origin` does not normalize as a remote at all, so the remote rung never participates. That is why FG-621's move of the dispatch substrate from linked worktrees to private clones silently blinded every clone-dispatched task, across runs, with nothing failing. The repair is WHICH DIRECTORY is asked — never a relaxation of the cross-repository guard, and never a path-prefix exemption for the clone directory; the project directory is carried forward AS DATA. An authority that still does not resolve dispatches as it always did, with an `unknown` marker, but the host now states the degradation and records it against BOTH THE RUN AND THE TASK (`container.backlog_authority_unresolved`, `payload.stage` distinguishing a `resolve`-stage identity refusal from a `publish`-stage failure of a cleanly resolved `db` authority) rather than leaving it discoverable only in the prose of the agent whose reads refuse — an event carrying the task alone lands on no run-scoped surface, and a ticket-blind task completes successfully rather than failing into the failure-derived task-side ones; a project declaring no `project_key` resolves `markdown` and stays silent. (FG-608, FG-666; see `docs/concepts.md` → Container ticket authority, `learnings/decisions/2026-07-29_container-backlog-snapshot-authority.md`, `learnings/decisions/2026-08-03_dispatch-backlog-authority-from-run-state.md`.)

21. **The dashboard's FG-679 serving and polling paths make no outbound call, and never reach a launch through a live probe.** No GitHub, no shell, no `git`, no Forge CLI, no tmux — and never `readLaunch` or `listLaunches`, whose status classification is a *live tmux probe* rather than a read of durable state. `Current activity` is a projection of persisted rows (`launch_observations`, the review-loop's `review_loop.ci_observed` observations, and task rows) and nothing else, which is what makes it safe for a server with no authentication to poll every two seconds. It is enforced by a **runtime guard** over those paths — spies over `child_process`, the `gh`/`git` binaries and outbound HTTP, driving real requests — not by source inspection, because inspection cannot see a call added three layers down. Two **pre-existing** serving paths do shell out and are RECORDED as named exceptions rather than absorbed into this rule or silently narrowed out of it: FG-290's `docker inspect` per running task on every `/api/in-flight` request (`dashboard/src/queries.ts:253` → `findReconcileCandidates` → `probeContainerLiveness`, `src/ops/reconcile-candidate.ts:63`), and project presentation shelling `git` (`dashboard/src/queries.ts:1371` `projectPresentation` → `repositoryCheckoutIdentity` → `execFileSync("git", …)`, `src/util/repository-identity.ts:13`). The guard is scoped to the new paths; it is not widened to cover those two, and it is not narrowed to pass over a path that does shell out. Progress that the dashboard could not otherwise see is persisted by extending exactly ONE existing Forge-owned observer — there is no second CI poller, no dashboard-side credential, and no second auth path. (FG-679 BD-7/BD-12/BD-13/BD-18; `docs/plans/fg679-current-activity-architecture.md`.)

22. **A launch is placed on a run or project ONLY by explicit submission-time metadata — never by its name, its argv, its log text, or `forgeIds`.** Association is structured data recorded when the launch is submitted (`forge launch run --run <run-id> [--task <task-id>] [--ticket <id>]`), and declaring one of those ids is the only thing that authorizes **run-level** placement, regardless of which channel resolved the launch's *project* directory. `association_kind` names that separate, weaker fact — **which channel decided the project home** (`explicit`, `cwd`, or `none`), not whether the launch is associated — so a launch that declared a run whose run row carries no registered project home still reads `cwd` (the cwd supplied the project) while staying on its declared run's Current activity, never demoted to `unassociated`. Where a declared association's project and the launch's cwd both resolve to registered projects and DISAGREE, the declaration outranks the cwd (FG-684): the launch is placed on the project its association names, never on whatever project the invoking process's cwd happened to sit in. A launch with no declared run/task/ticket and a cwd that maps to a registered project home is placed at **project level only**, marked `unassociated`; a launch with neither a declared id nor a cwd resolving to a registered project home lands in the host-level **Unassociated activity** bucket, which is what lets `/status` and the dashboard agree without inventing ownership. Inference is prohibited rather than merely discouraged: FG-492 records that long-lived agent processes carry conversation text in argv and falsely match unrelated role and ticket names, so a launch whose name or argv mentions a run is *not* thereby that run's. `extractForgeIds` — which regexes `run-…`/`task-…` out of raw log output and publishes `forgeIds` on every `LaunchView` — is QUARANTINED, not removed: it stays for compatibility and diagnostics and authorizes nothing. The corollary holds on the rendering side: a persisted observation carries the STRUCTURED launch status, never a pre-rendered string, so `statusLine` remains the one human rendering and `terminated by SIGTERM (signal sender not recorded — origin unknown)`, a bare signal-range `exited 143 (signal-range code, no signal evidence — origin unknown)`, `owner gone` and `unknown` stay four different facts on every surface — none of them a generic `failed`, and exit 143 alone is never attribution evidence. A stale or incomplete observation reads `unobserved since <time>`: never fabricated as `running`, never fabricated as terminal. (FG-679 BD-2/BD-3/BD-4/BD-12/BD-14/BD-15; FG-684 AC4; see `docs/concepts.md` → Current activity.)

23. **Queue membership is planning intent; execution authority is a separate explicit act, and the capacity ceiling binds only what it counts.** Enqueuing a ticket never authorizes a container — arming autonomous dispatch does, it records who and when, and it stays CLI-only (`forge queue dispatcher arm`; FG-591 D2). `max_active_runs` is a hard bound on **queue-owned** concurrent runs, counted as live `queue_claims` rows **inside `claimNextEligible`'s write transaction**, host-scoped, with a host-wide value: a ceiling checked anywhere else is advisory, over-admits silently, and leaves no trace. Every other kind of Forge work — operator-initiated runs, campaign items, review loops — carries no claim row, is invisible to that count, and is REPORTED beside the ceiling and never subtracted from it, because a subtraction taken outside the admitting transaction reads as a guarantee while being a guess. **Disable and capacity reduction are admission tests, never reapers** (FG-591 D5): running work keeps running, its claims keep being heartbeated, and the dispatcher process keeps renewing — stopping it would drop heartbeats, lapse leases, and let a takeover launch a duplicate. **An operator dequeue, unrank or defer never releases a live claim** (FG-591 D4): cancellation is the separate explicit `forge queue cancel`, which stops the work FIRST and lets the claim's own lease owner retire the reservation, so "not a queue member and still executing" is a real, first-class board state rather than a gap. **`blocked` and `in_progress` are derived on every read and never stored** — the board's five views are projections over rank, membership and lifecycle status plus evidence, not a second mutable status vocabulary — and a temporary scheduling incompatibility is dispatcher scan evidence, never a `blocker_evidence` row, which is durable, per-ticket, container-visible, and would otherwise reinterpret that ticket's status for every agent container on the next publish. Bypassing an incompatible candidate leaves its durable rank unchanged; the dispatcher never reorders the operator's queue, and never re-authors its own eligibility (FG-591 D7).
